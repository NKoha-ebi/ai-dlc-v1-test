## 1. 推奨と採用境界

環境分離は案2「ローカル開発＋検証／β別プロジェクト」を推奨する。安全制御用・復旧用プロジェクトも別に置くため、実際のクラウド総数は6。Emulatorでは実IAM・地域障害・ネットワークを検証できないので、検証環境に本番相当の配置を用意する。[配置比較](deployment-architecture.md)と[共有基盤](../../shared-infrastructure.md)を参照。

本構成は比較試作候補。大阪制御正本の永久喪失、安全変更の別障害範囲への耐久化、2秒以内の遮断、受信完全性を解決済みにしない。本実装の仮採用は試作証跡を含む再レビュー後とする。試作範囲の計画承認と、実環境作成・送信の許可も分ける。

## 2. 部品とサービスの対応

識別名はすべて仮称。Tは東京asia-northeast1、Oは大阪asia-northeast2を表す。β・検証の各組に以下を作る案とする。

| 論理部品／重要度・停止影響 | サービス・配置 | 入出力・依存・権限境界 |
| --- | --- | --- |
| SPA／高・入口停止 | Firebase Hosting、静的ファイルのみ | ブラウザー→認証／API。本文・PDF・再設定秘密をHostingに置かない |
| 業務バックエンド／高・保存等停止 | Cloud Run business T、同一イメージの待機O | 資格と版付き要求→制御仲介。DB・AI秘密を持たず、任意本文取得APIを設けない |
| 認証・目的別認可／高 | Firebase Authentication、C03/C04、制御仲介 | IDトークン→現在のAccount・同意・世代判定。Authの地域はDB配置と別 |
| 要求台帳・枠・安全制御／高 | controlプロジェクトのFirestore O、Cloud Run control O | 本文なしのOperationId・AttemptId・安全変更・世代。安全変更の独立保護先は未成立 |
| 最終読取返却・書込／高 | controlと同じ信頼境界のCloud Run executor O | 所有元の操作契約を実行。制御DBと業務DB間の原子性はない。本文を扱うため台帳プロセスと権限を分離 |
| 外部AI送信／高・AI停止 | Cloud Run送信経路O、Secret Manager | 検査済み最小入力→Responses。予約と実送出の順序保証は試作必須。業務プロセスから直接送信不可 |
| PDF実行／高・PDF停止 | 同一コードのPDF実行配置、Cloud Storage一時領域O | 確認済み版のみ。Chromiumの外部URL・任意ファイル取得を拒否。取得も仲介して毎回再認可 |
| 相談・属性・版／高 | Firestore Standard T、recoveryプロジェクトの待機DB O | executorだけが業務書込。一般更新と複製outboxを同一DBトランザクションへ |
| 複製・復元／高 | 同一コード内部ワーカー、Tasks T/O、Storage O | 版付きグループ→待機DB・整合点。キューは本文なし、本文は保護された記録参照 |
| 削除・復元物隔離／高 | 制御DB一覧、専用削除ワーカー、Scheduler O | 元期限・世代→DB、Auth、PDF、コピーの削除証拠。アクセス不能は消去済みではない |
| 通知・権利請求／高 | 独立Cloud Run入口O、SES東京送信、独立メール受信契約候補 | 受信記録→本人確認→遮断意図。SES送信だけでは独立受信メール箱を提供しない |
| 監査・観測／高・欠測時停止 | Cloud Logging地域別バケット、Monitoring、Trace、別地域監視 | 本文なしイベント・操作別計測。監査権限と運用集計権限を分離 |
| 運営・内部集計／中（公開・権限操作は高） | 同一バックエンド内C10〜C16 | 案件許可と別人確認を継承。運営資格にインフラ管理・全本文閲覧を付与しない |
| 配備・復旧／高 | GitHub Actions＋Terraform案、Artifact Registry国内 | 承認済みダイジェスト・設定版→環境。復旧担当と再開確認担当を分ける |

業務サービスの所有責務・作業単位U01は増やさず、同一コードの起動モードとサービス資格を分離する。重要度は[非機能要件](../nfr-requirements/nfr-requirements.md)を継承。新しい配置を単一プロセスのまま全資格付与する構成は不採用。

## 3. 初期設定候補

| 対象 | 提案初期値 | 根拠・確定試験 |
| --- | --- | --- |
| business T | 1 vCPU、1 GiB、min0／max4、concurrency8、HTTP timeout60秒 | 承認済み枠案を継承。20仮想利用者の通常API p95 2秒・成功率99.5%以上。コールド起動含む。min1代替費用を比較 |
| control／executor O | 各1 vCPU、1 GiB、min0／max4、concurrency8 | 単一インスタンスロックに依存しない。直前停止・再開試験で同世代撤回・旧世代を検証。未達ならmin1または方式再設計 |
| PDF配置 | 1 vCPU、2 GiB、min0／max2、concurrency1 | 全環境共通のPDF枠1を台帳管理。メモリー不足・55秒・通常保存への波及を測る |
| AI枠・期限 | 全体2枠、外部待機45秒、サーバー目標55秒、画面60秒、要求5分終端 | 待ち行列も含む。枠不足は受付前拒否。成否不明の外部送信を自動再試行しない |
| 通常DB／内部HTTP | 全体2秒内に収まる残時間予算、個別SDK試行の上限1秒案 | 下位リトライ込みで残時間を伝播。安全遮断の2秒条件は別途検証。1秒超で成功を仮定しない |
| メール | 受付p95 5秒、配送HTTP試行上限5秒案 | 耐久受付と実配送を分離。配送不明の盲目的再送なし |
| 依存回路 | 5連続失敗で60秒遮断、合成1試行で半開 | DB・AI・PDF・メール別。AI不調で通常保存を再起動しない |
| Tasks | 削除／複製／通知を別キュー、dispatch 2/秒・同時2から開始 | ID・種別・世代のみ、OIDC audience固定。安全判定は実行時再確認。AIの外部再送をTasksのretryへ委任しない |
| 起動回収 | Scheduler毎分、未登録outbox・要求期限・削除期限を走査 | 作成と登録は非原子的。期限の近いものを優先、失敗は通知。キュー滞留を期限延長に使わない |
| 複製監視 | 整合点遅延15分警告・1時間重大 | 一般RPO4時間を待たない。欠番・部分グループも警告。安全変更にはこの遅延許容を使わない |

max4は厳密な外部課金上限ではない。新旧リビジョン・切替先をまたぐAI/PDF枠と予約を制御正本で共有し、インスタンス増加で倍増させない。RunリージョンCPU・IP容量、Firestore文書／トランザクション、Tasks dispatch、Authメール／試行制限、外部AI RPM／TPMを実アカウントで確認し、使用率80%で警告する案。増枠は負荷・費用再レビュー後。

## 4. ネットワークとIAM

入口はHostingの静的配信とHTTPS API。業務APIはFirebase IDトークンを検証する。内部control／executor／workerは公開未認証呼出しを禁止し、呼出元別サービスアカウントとRun invokerを限定する。独立権利請求入口は東京のAPI・DBを必須依存にしない。ブラウザーの医療本文Firestore直読・公開Storage・長寿命署名URLは不採用。

送出はDirect VPC egressのall-trafficと明示許可経路を候補にする。businessにはDB更新・外部AI／SES秘密・他サービスアカウント偽装を与えない。外部通信は送信配置のみから、NAT／制御プロキシ経由とする。プロキシ、Google API宛て経路、DNS、既存接続、IPv6、旧リビジョンを含め直接送出の抜け道を試す。APIエンドポイント用PSC・内部LB等の必要部品は接続試作で確定し、費用枠に含める。FQDNだけで厳密な送信遮断が成立するとはしない。[Direct VPC公式仕様](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc)。

| 資格 | 許可 | 与えない権限 |
| --- | --- | --- |
| business-sa | 指定control／executor呼出し、最小ログ送信 | 患者DB IAM、外部秘密、SA token作成、復旧DB |
| control-sa | 制御DBの必要読書き、指定executor呼出し | 患者本文の一般読取、外部AI秘密、IAM編集 |
| executor-sa | 現在の対象DBへの必要読書き、対象PDFオブジェクト | Owner／Editor、任意DB export、復元一覧の自己承認 |
| sender-sa | 指定秘密版のaccess、送信試行契約 | 任意本文探索、IAM編集、予約なし送信 |
| replication-sa | outbox読取、待機DB適用、整合点記録 | 公開操作、外部送信、復元先の業務開放 |
| deletion-sa | 対象DB／オブジェクト削除、結果追跡 | 業務開放・復元承認。Auth削除は専用資格へ分離 |
| task-invoker-sa | 指定workerのinvoke | 台帳・本文・秘密アクセス |
| CI資格 | 短期OIDC、環境別plan／承認済みapply | PRからβ秘密・患者データ取得。常設鍵は作らない |
| 復旧実行／再開確認 | 期限付き昇格、操作と承認証跡 | 通常運営資格への自動付与、単独の自己承認 |

FirestoreサーバーSDKはSecurity Rulesを認可境界にできない。IAMでDB境界を制限し、コレクション単位の業務認可は所有元契約で検証する。DB単位の条件・カスタムロールの有効性は負試験で確認し、不可能な粒度をあるものとして記載しない。必要なら別プロジェクトへ分け再見積りする。[Firestore IAM](https://docs.cloud.google.com/firestore/native/docs/security/iam)。

## 5. 保存・復元・消去

一般主系Firestore T、待機Firestore O、PITR最大7日・日次バックアップ28日を候補とする。標準restoreは同じロケーションに限定されるため、東京バックアップから大阪へ直接restoreする手順は使わない。[restore公式仕様](https://docs.cloud.google.com/firestore/docs/reference/rest/v1/projects.databases/restore)。

一般更新とoutboxを同一主系トランザクションで保存し、Oへ版・削除・整合グループを適用する。日次の整合基準点と増分をOから取得可能にし、更新グループの全適用とチェックポイントを確認する。基準点生成は書込停止または整合時刻指定の対応可否を試作し、単なるexport開始時刻を整合点にしない。待機DBの破損に備えたO側世代保存も作成元・元期限・ハッシュ・復元可能点で一覧管理する。

PDFは生成開始から24時間、主要データは削除受付確定から7日、バックアップ由来を含め35日、最小削除追跡は完了後180日上限を維持する。28日バックアップでも7日目直前のデータが35日を超えないか、時刻・実削除遅延込みで確認する。安全余裕が取れなければ保持日数を短縮する案を再レビューする。PITR・バックアップ・export・複製記録・Auth・メール・隔離DBすべてを削除一覧へ含める。

TTL／Lifecycleは補助。期限前の明示削除、サブコレクションを含む残存照合、完了証跡を必要とする。Cloud Storageのsoft delete・Object Versioning・保持ロックが元期限を超えるコピーを残さない設定を検証する。復元コピーで元期限を再起算しない。[Firestore削除仕様](https://firebase.google.com/docs/firestore/manage-data/delete-data)。

旧東京不通時の物理消去は管理APIも障害になり得る。アクセス遮断と消去証明を分け、7日／35日以内に実消去を証明できない障害範囲は未達とする。構成やポリシーの変更が必要なら要件へ戻す。隔離しただけで期限達成としない。

## 6. 認証・地域・外部保持

[追加認証対策の補完案](../nfr-requirements/authentication-supplement.md)を作成した。メール確認・不正試行制限・運営TOTPの採否は補完レビュー待ち。標準再設定RESTの迂回、24時間・最新のみ・遅延管理処理の競合は別の成立試験であり、TOTP導入だけでは解消しない。

Firebase Authは米国処理等を含むため、国内Firestoreで全データ国内固定とはしない。[Firebaseプライバシー](https://firebase.google.com/support/privacy)。Loggingは地域バケットを使う候補だが、管理ログ・既定バケット・提供元処理も別に確認する。[Logging地域](https://docs.cloud.google.com/logging/docs/region-support)。

OpenAIはResponsesのstore:false、最小入力、ツール・背景処理なしを継承。既定の不正利用監視保持とアプリ状態保存は別で、日本の保存設定は国内推論の保証ではない。MAM／ZDRや実アカウントの適用可否、削除期限・例外同意を確認するまで患者データ送信を有効化しない。[公式データ管理](https://developers.openai.com/api/docs/guides/your-data)。SES東京、独立受信メール、Hostingにも同じサービス別地域・保持・削除確認を行う。

## 7. 監視・通知・配備

通常操作6経路を1分ごとの1つの合成実行にまとめ、経路ごとに結果を保持する。AIは別の5分実AI監視、PDFは実PDF経路、独立入口／監視欠測は別地域の到達監視で検出する。監視障害が同時に及ぶ範囲と国外実行地点を確認し、地点追加時は再見積り。1地点の正常を全世界の保証としない。

Loggingに本文なし構造化ログ、Traceに要求／内部呼出しの相関、MonitoringにAPI別p95・成功率・停止区間、CPU／メモリー／枠、クォータ、複製点・バックアップ・削除期限・キュー年齢・予算予約を定義する。ダッシュボードは通常操作、AI/PDF、安全・DR、費用の4面案。診断ログ30日、本文なし試験／変更証跡90日を提案値とし、個人対応記録は元の削除期限を優先する。管理ログの固定保持とリクエストURL等は実設定確認事項。

livenessはプロセス自身、startupは起動完了、readinessは現在必要な認証・DB・制御経路を確認する。Cloud Runのprobe／routing対応を構築時に固定し、サポートを確認していないdeep readinessをLBが自動判定すると仮定しない。アプリの操作拒否と合成監視も併用する。[Cloud Run health checks](https://docs.cloud.google.com/run/docs/configuring/healthchecks)。

通知先は障害用・権利請求用・認証用を分離し、同一チームの実担当と別の再開確認担当をβ初回前に確定する。SESは送信候補、独立受信箱は別契約候補であり、実宛先・ドメイン・送信許可は未取得。通知不着・欠測を正常にしない。問い合わせのアプリ内返信を勝手にメール送信へ変更しない。

Canaryは既存の5%→25%→100%、各段階最低15分、API別確定100件、早期停止・欠測・保留後明示再開をそのまま継承する。AI/PDF各10試行（正常4・時間切れ2・重複2・遅延2、AI正常に実AI最低1）を省略しない。詳細は方式第3節を正本とし、Cloud Runの比率変更だけでゲートを実現済みにしない。

## 8. 費用・レビュー条件

[月100相談の通常月概算](cost-estimate-100-consultations.md)を費用の正本とする。予備費・常設検証・月割復元試験の一律枠は0。固定ネットワーク以外は約47〜63 USD／月、旧固定55 USDを残した比較は約102〜118 USD／月。固定経路と独立安全保護先の追加費用は未確定。旧850 USDの予算推奨と一回100 USDの試作枠は採用しない。試験月の費用は実施計画と使用量で別途算定する。

費用低減は監視頻度や安全保護を勝手に省く方法で行わない。実使用量・接続部品・MFA構成・独立保護先が変われば再計算する。高ケースへ近づく場合はAI上限・予算と方式を再レビューする。削除・監視・復旧枠をAIに使い切らない。
