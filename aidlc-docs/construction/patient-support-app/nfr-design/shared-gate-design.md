# 共通ゲートの設計方針

2026-11-15。ユーザーの「費用の面で、ゲートを共通にします。設計の内容を変更して下さい」を反映。本書をゲートの共有方式・増設・費用数量の正本とし、旧利用者別VMの比較案に優先する。

## 1. 変更した決定

| 項目 | 現行方針 |
| --- | --- |
| 実行基盤 | 複数利用者で共通の送信ゲート・返却ゲートを利用する。利用者専用VM・専用ゲート資源は前提にしない |
| 役割 | 最終送信と最終本文返却は別の論理役割・資格を維持。共有とは利用者間の基盤共有であり、すべての役割を無条件に1プロセスへ統合する意味ではない |
| 利用者の分離 | 本人・対象・目的・同意・版・期限・停止状態を要求ごとに判定し、データ・試行・接続を利用者別に管理する |
| 個別停止 | Uを停止しても正常なVの処理は継続できることを引き続き設計条件とする。VMの物理分離は要求しない |
| 全体停止 | 共有制御の故障、対象範囲不明、利用者間影響を否定できない場合は全体閉鎖する。全体停止だけで個別停止の条件を満たしたことにはしない |
| 数量 | 登録人数とVM台数を対応させない。初期台数・上下限・増設条件は同時20人と既存性能・安全条件への検証結果から確定する |
| 製品・価格 | Cloud Run／VM等の具体製品・初期台数・確定料金は未決定。共通化の方針を決定したもので、未成立の現試作を本番採用する決定ではない |

以前のAC-01回答は「利用者別隔離」を求めたもので、利用者ごとのVMを選択した回答ではない。本変更では共通基盤内での利用者別認可・停止として具体化する。今回の指示を、対象者だけを止められなくてもよいという条件緩和に読み替えない。

## 2. 共通経路の責務

業務処理は、対象と目的に束縛された最小限の送信要求を共通送信ゲートへ渡す。ゲートが現在の利用者状態・対象版・同意・世代・期限を確認して固定宛先へ送る。業務処理には外部AI資格・自由URL・直接送信経路を与えない。

返却は、業務結果・AI結果・PDFを共通返却ゲートへ渡し、接続の本人と結果の対象が一致することを確認して一括返却する。共通キャッシュ・接続pool・待ち行列を介して別利用者の本文を返さない。直接Storage URLや旧公開URLからの迂回を許可しない。

| 共有するもの | 利用者・要求ごとに分けるもの |
| --- | --- |
| 送信／返却のサービスコード、配備・監視、共通実行資源 | 本人と対象、目的・同意・対象版、制御世代・元期限 |
| 各役割の最小権限資格と接続の管理機構 | 操作ID・試行ID・実行者、socketの所有者、処理結果と返却先 |
| 安全な共通スケジューラーと処理枠 | 待機中／実行中の対象、停止範囲、重複排除、利用者別の処理量 |

共有資格は患者データの利用許可を代替しない。Uの要求にVのIDを混ぜた場合、再利用した接続・cache・PDF参照・結果IDを含めて拒否する。内部サービス認証と患者の業務認可を別に検査する。

## 3. 停止・障害・更新

対象別の停止状態は全共通インスタンス・旧世代・待機系で確認する。ローカルメモリーに停止flagを置くだけで全体適用としない。停止したUの待機要求・古い許可・再接続は新規作用として拒否し、正常なVの要求と混同しない。

D-01〜06・W-01〜04・G-01〜04を維持する。開始済みの同じ送信・返却の完了例外と、新規開始禁止を区別する。業務DBの禁止更新と保存の同一トランザクション、二地域耐久受付、元期限、未確認時Pendingの扱いも継承する。

共有プロセスの停止・更新・過負荷・共通資格やproxyの障害は複数利用者に影響する。個別停止と共通障害を別ケースとして記録する。共通化したことだけで最終確認と実ネットワーク引渡しの競合PG-01や旧主体排除PG-02が解消するわけではない。[旧検討の反例と証拠](per-user-gate-feasibility-review.md)のF-01〜04は、現行経路に合わせて検証へ引き継ぐ。

更新は[一括公開方式](beta-bulk-release.md)に従い、全旧送信／返却主体と既存接続の遮断証拠を確認してから新版だけを開く。証拠不足では閉鎖を維持する。共通gateを1台と仮定して旧主体の棚卸しを省略しない。東京・大阪の二地域保護と単独昇格禁止を維持する。

## 4. 容量と後日の増設

初期の必要容量は登録100人・同時20人・月100相談、既存の通常API性能、AI／PDF実行枠と期限を満たすことを条件とする。共有処理枠と利用者別の公平性を検証し、一人の重い要求が他利用者の通常保存・一覧を圧迫しない構成にする。具体的な初期台数・上下限は未確定。

増設時は新インスタンスにも同じ認可・停止世代・接続所有者の照合を適用する。共通の重複排除・期限・処理枠を使い、台数増加で外部AI二重送信や利用上限の倍増を起こさない。削減・終了時は新規割当を閉じ、未知試行・接続・旧実行者を照合する。共有サービスを増設することと、古い実行者を排除せず新世代を開くことは区別する。

## 5. 費用の数え方

利用者100人だから100台、同時20人だから20台という積算を取りやめる。送信・返却それぞれの共通poolについて、地域別の実インスタンス時間・CPU／メモリー使用量・disk等の存続量を数える。Cloud Run等を選んだ場合も、その製品の課金単位を用い、VM時間の式をそのまま使わない。

VM候補の実行費＝各地域の共通送信poolのVM時間×該当単価＋各地域の共通返却poolのVM時間×該当単価。そこへdisk・backup・待機資源・LB／proxy・IP／NAT・通信・監視・秘密・DBと外部AI等を加える。同じ資源を両役割が共有すると正式に決めた場合のみ重複を除く。

数量の説明例として、東京の送信poolを1台・返却poolを1台、各720時間稼働させる仮定なら合計1,440 VM時間／30日。これは初期2台の採用決定ではなく、待機系・複数zone・容量・旧主体の証拠も未算入の算術例。1台常時稼働を追加する差は720 VM時間／30日。disk等は別計上する。

会話中の「1台月10 USD」「95〜99%削減」は仮単価による比較例であり、確定料金・削減保証ではない。利用者専用VMの72,000／14,400 VM時間や2,000 GiB月は旧比較例として履歴に残すが、現行予算に使用しない。既存の費用正本の未確定総額や残存費目を0にしない。

## 6. 検証と残課題

| 必須確認 | 判定条件 |
| --- | --- |
| 利用者別の認可・接続・結果の対応 | Uの要求にVのID・接続・cache・結果を混ぜても拒否。正当なVの通常処理は継続 |
| 利用者別停止と旧許可 | Uの全実行者・待機要求・再接続を拒否し、停止後の新規作用を排除。最終確認直後の休止・復帰を含む |
| 共通障害・過負荷 | 欠測・対象不明は閉鎖。利用者別制御と共通障害の影響を区別して通知・復旧する |
| 多インスタンスと増減 | 新旧混在・応答喪失で二重送信、上限倍増、期限延長、停止flagの脱落を起こさない |
| 一括公開・災害復旧 | 全旧経路遮断、二地域確定点、独立保護、未知試行照合、別担当開放の証拠がそろうまで再開しない |
| 費用と容量 | 同時20人の既存受入条件、実資源量・存続時間・地域単価を確認し初期台数・費用を決める |

PG-01〜04、二地域復旧、共通poolの容量・quota・公平性、製品・初期台数・実単価・総額は未確定／未実証。今回の作業は共通化への文書変更であり、検証資材・アプリのコードは変更していない。将来のコード変更は具体計画へ反映してレビューする。
