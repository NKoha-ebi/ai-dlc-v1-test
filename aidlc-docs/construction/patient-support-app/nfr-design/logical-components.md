# U01 非機能設計：論理部品と接続

2026-11-05。レビュー案。[設計方式](nfr-design-patterns.md)と併せて承認対象。単一バックエンド内の責務を具体化し、新しい利用者機能・研究実データ・別作業単位を追加しない。

## 1. 所有責務と論理部品

| 論理部品 | 既存責務との対応 | 入出力・保持境界 |
| --- | --- | --- |
| 認証・目的別認可 | G1 C03・C04、各所有元、C12 | Firebase資格→Account／資格世代・同意・目的・案件許可・公開状態の判定。本文の無条件取得権限を発行しない |
| 要求台帳 | C05・C06・C07とC15保存実装 | 本人・要求ID・RequestKey・入力／参照版・期限・試行状態。本文は所有元の許可参照に分離 |
| 実行枠とフェンス | 共通基盤、業務上限は各所有元 | AI／PDF別の上限・要求ID・リース・有効世代。インスタンス数と独立した全体上限 |
| 送信調整 | C06、C03・C04・C09の現在状態 | 許可済み最小入力と送信予約。識別情報除去・直前版照合・遮断順序を確認して外部送信 |
| PDF実行 | C07、C05の確認済みSnapshot | 本人・有効版・要求ID→期限付き成果物。外部URL取得・AI再生成なし |
| 削除調整・期限管理 | C09が調整、各所有元が実施 | 受付時刻・対象派生先・期限・結果を追跡。部分失敗を完了にしない |
| 安全変更保護 | C03／C04／C09の正本責務＋C15 | 本文なし変更証跡・世代・最終確定点。別地域に耐久保存。業務正本を台帳へ移さない |
| 一般データ複製・復元 | C15、各所有元 | 版付き更新グループと削除を待機DBへ適用。本文を含むため患者データと同等に保護 |
| 監査・稼働観測 | C16 | 監査と運用メトリクスを論理分離。本文・秘密・完全なURLを保存しない |
| 通知受付・配送 | C13の通知要件、C03認証回復、C16障害通知 | 受付ID・宛先・テンプレート・状態。患者本文を送らず、通知種別ごとにアクセスと期限を分離 |
| 配備・構成・復旧制御 | G1基盤、C12公開制御と連携 | 成果物版・構成版・承認・書込先・フェンス世代。日常運営ロールへクラウド管理権限を自動付与しない |
| 移行照合 | C15と各所有元 | 移行ID・元版・件数・参照・ハッシュ等の照合結果。専用の常設業務サービスは不要 |

G2のC01は状態・入力保持を表示し、C05が未確認AI案と確認済み版を管理する。G3のC02・C10〜C13は既存の案件許可・別人公開確認を維持する。G4のC14は研究条件承認・同意を別々に判定し、ベータ実データは無効のままとする。共通基盤から所有元Repositoryを直接変更して業務制約を迂回しない。

## 2. 接続と障害境界

1. ブラウザーは認証後にバックエンドへ要求する。Firestore医療本文・外部AI・秘密管理へ直接接続しない。
2. アプリケーションサービスは必要な所有元の判定を組み合わせ、要求台帳と版を確定する。
3. 通常保存は主系Firestoreで期待版とRequestKeyを検証して確定し、同じトランザクションで複製用記録を残す。複製失敗は監視・再試行するが、主系成功を待機系確定と説明しない。
4. AI／PDFは別枠を取得し、現状態・公開状態・期限を照合する。AIは最小入力の検査と送信順序制御を通す。保存・表示前にも再検証する。
5. 安全変更は主系遮断→保護先の確定判断→両系照合を追跡する。保護先障害では新規の成功確定を止め、主系でできる遮断は維持する。
6. 削除・メール・複製の再開可能処理は永続要求を起点に起動する。キューが遅延しても期限を延長しない。
7. 監視は操作別の合成結果と資源状態を受け、別地域からの欠測確認とメール通知を行う。同じDB障害で監視記録まで失う範囲を明示する。

単一バックエンドのためプロセス障害の完全分離は保証しない。実行枠・メモリー上限・期限・外部依存の回路遮断で影響を抑え、PDF負荷で通常保存が受入条件を満たさない場合は同一コードの実行配置を見直す。独立業務サービスへの分割を自動決定しない。

## 3. 永続キューの比較と提案

| 方式 | 利点 | 注意点・判断 |
| --- | --- | --- |
| インメモリー待ち行列 | 単純 | 再起動・scale-to-zeroで要求を失う。耐久的受付が必要な処理には不採用 |
| Firestore要求台帳＋定期走査 | 状態と再開を一元化 | 起動遅延・走査費用・競合制御が必要。キュー登録漏れの回収経路として採用 |
| Cloud Tasks＋要求台帳 | 配送・流量制御を分離 | 重複実行を前提にアプリで重複排除。リージョン障害時は新主系の台帳から再構築 |

Cloud Tasksを削除・複製・通知など再適用可能な処理の起動案とし、要求台帳を正本にする。[公式の重複実行制約](https://docs.cloud.google.com/tasks/docs/common-pitfalls)と[再試行設定](https://docs.cloud.google.com/tasks/docs/configure-retry-task)を確認した。タスクの存在を業務成功と扱わない。payloadは要求ID・処理種別・世代のみとし、本文や再設定生トークンをキューに複製しない。

台帳保存とキュー登録は別システムなので原子的ではない。台帳の起動待ち状態→登録→受理の記録を持ち、定期走査で未登録を回収する。重複配送は所有元の版・状態・要求IDで無害化する。削除等の冪等処理は指数バックオフを使うが、期限超過は通知し失敗を隠さない。

AI要求を起動する場合も送信予約の取得は一回のみとし、重複配送が外部再送にならない状態遷移を要求する。送信予約後にプロセスが落ちて送信の有無を判定できなければ成否不明のまま終端化する。キューの自動再試行に外部AI呼出しを任せない。ワーカー認証・地域提供は[Cloud Tasks地域](https://docs.cloud.google.com/tasks/docs/locations)とIAMでインフラ設計時に確定する。

## 4. 状態と版の契約

| データ | 最小項目・不変条件 |
| --- | --- |
| Request | ownerId、purpose、requestId、key、expectedRevision、inputVersion、referenceVersions、createdAt、deadline、status、attempt。本人＋同一キーは同じ要求へ収束 |
| Slot | 種別、要求ID、リース期限、フェンス世代。期限切れだけで成否不明のAI費用枠を解放しない |
| SafetyChange | 変更ID、対象ID、目的、種別、世代、順序、確定段階、時刻、元期限。本文・メールを含めない |
| ReplicationGroup | 更新ID、元版、整合グループ、対象、削除状態、内容参照／内容、適用版。安全台帳とは別データ |
| Checkpoint | 基準点、反映順序、確定判断、フェンス、整合性証跡。最大連番だけで末尾確定としない |
| DeleteProgress | 申請／遮断／受付確定時刻、派生先、主要・バックアップ期限、完了証跡。再試行で起算し直さない |
| MailRequest | 通知種別、要求ID、宛先、テンプレート、受付・配送状態、期限。配送成否不明と確定失敗を区別 |
| ResetRequest | ハッシュ、世代、有効期限、消費段階、資格失効状態。生トークンは恒久保存しない |
| MigrationManifest | 移行ID、元環境、対象と元版、スキーマ版、照合結果、元期限、最終安全確定点。再実行で状態を復活させない |

これは物理スキーマ確定ではなく契約案。C03・C04・C05等の既存エンティティを重複正本化しない。原子的に守る条件と外部システム間で段階追跡する条件を分離し、HTTPパス・索引・トランザクション上限は後続で具体化する。

## 5. 監視と管理経路

監査は実施者・目的・対象・操作・結果・版・時刻・要求IDを最小限保存する。運用観測は時間・成否・枠・キュー年齢・資源・複製遅延等を記録し、患者IDをメトリクスラベルへ載せない。エラーのスタックにも本文・資格を埋め込まない。

主系とは別地域の監視から認証・保存・公開状態・削除受付・AI・PDF・運営操作を合成データで確認する。外部通知の到達確認と欠測を追跡する。アラートが届かない状態を正常扱いにしない。

C12の公開制御が停止した場合に備え、管理IAMに限定した緊急の遮断・固定案内の配備経路を持つ。日常の運営アカウントからこの経路を使用しない。復旧時は認証と安全台帳の確認を迂回せず、緊急操作も後から変更記録と照合する。

## 6. 検証と後続設計

純粋な状態遷移・保存変換はfast-checkで往復・終端不変・重複適用・世代単調性・保持期限不延長を検証する。有効／無効版・欠落／不明／非開示・Unicode・期限境界の構造化生成器を共通化し、縮小とseed/pathの再現をCIへ含める。分散障害・実認証・地域喪失はPBTだけでは検証できないため合成環境で故障注入する。

インフラ設計へ渡す項目は、地域・プロジェクト／DB分離・IAM・鍵・ネットワーク・キュー・スケジュール・ログ保持・バックアップ・配備先・切替導線・費用積上げ。構築・実行は未実施。拡張適合の規則別一覧と成立条件は[方式文書第10節](nfr-design-patterns.md)を共通評価とする。
