### S1の接続と権限

ブラウザーは静的UIと認証を経て共通returnへ接続する。returnが患者本文を返す唯一の業務入口となり、businessは内部要求だけを処理する。businessからwriterへ保存を依頼し、AI入力は共通send、PDF生成はPDFへ依頼する。患者へのAI結果・PDFは再度returnを通す。業務応答を無検査でそのまま返す経路を作らない。

| 主体                  | 最小権限と利用者別の検査                                                                   | 依存喪失時                                                                                   |
| --------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| return／return-sa     | 認証済み接続とAccountId・対象・結果ID・目的・現在版を照合。Storage直URLを発行しない        | 必要な制御が確認できない対象の本文を拒否。本文なし状態確認・案内・ログアウトは既存例外内のみ |
| business／business-sa | 内部要求のみ。本人・対象を引き継ぎ、外部AI秘密・直接患者返却・本文DB直接書込み権を持たない | 依存失敗を正常結果にしない                                                                   |
| writer／writer-sa     | 業務DBの禁止文書と通常書込みを同一トランザクションで照合。対象をサーバー側で認可           | 禁止更新後の通常保存を拒否。競合再試行も元期限を維持                                         |
| send／send-sa         | 固定AI宛先・必要な秘密だけ。本文参照も対象限定APIを通す。任意URL・redirect・再送を禁止     | AIの成否不明は枠と予算予約を維持。保存・返却の可否を別に再判定                               |
| safety／safety-sa     | 東京・大阪の安全台帳と本文なし受信記録。利用者別停止・禁止適用要求・照合                   | 片側確認不能はPending、単独Accepted・単独昇格を禁止                                          |
| PDF／pdf-sa           | 確認済み対象版だけを読み短期保存。returnへ保護参照を渡す                                   | 遅延結果を元期限後に保存・返却しない                                                         |

Cloud Tasksの配送は起動契機とし、台帳を処理の正本とする。sendの再配送で新しいAI送信を起こさない。安全台帳に本文を保存しない。一般データの東京→大阪複製と、両地域で確定する安全記録を別の経路として扱う。

外部入口は外部Application Load Balancer＋serverless NEG＋returnのingress制限を検証する。内部サービスは内部ingressと宛先限定Invokerを併用し、default URL・tag URL・旧revision・Storage URLを含む迂回表を作る。業務側はDirect VPC egressのall-trafficを候補に宛先を制限する。NATは送信元変換であり宛先認可や停止フェンスではない。許可されたGoogle API経由の搬出も別途拒否試験する。

共通L7 proxyが本文を保持・送出する場合、returnのwrite完了だけでG-01の最終本文引渡しを観測したことにはしない。proxyを含む最終経路と観測点を確定できなければPG-01は未達のまま。本構成の説明を追加しただけでこの境界は解決しない。

| 経路             | 定義済みの論理責務                                                | 実配備で確定すべき境界                                                                            |
| ---------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 外部AI送信       | businessからsendだけへ依頼し、sendが固定宛先へ最小本文を送る      | TLS・HTTP実装・OS・中継を含む実本文引渡し箇所と観測証拠、停止との排他。write呼出し記録は代替不可  |
| 患者への本文返却 | AI結果・通常取得・PDFをreturnへ集約し、本人・対象・版を再検証する | LB／proxyが本文を保持して患者へ送出する場合の最終主体と引渡し開始。returnのOS引渡しと同一視しない |

研究開示に残る「撤回前の開示許可確定なら、その後に配送開始できる」という機能設計の変更案は、β対象外の別契約である。患者向けAI／PDF／本文返却へ流用せず、D-01／G-01の実開始済み例外を維持する。研究を将来有効化する場合は、この別境界とゲートの適用範囲を再照合する。

## 3. 容量・増設の試験開始設定

登録100人・同時20人・月100相談を維持する。次表は採用値ではなく測定開始値。通常APIの既存最大4・concurrency8、AI全体2枠・PDF全体1枠を基に、役割ごとの検証設定を明示する。

5役割の0.5 GiBは小容量で測定する比較案で、インフラ本文に残るbusiness／control等の1 GiBを性能根拠なく置き換える採用値ではない。起動・ピークメモリー・OOM・p95・費用を0.5／1 GiBで比較し、採用設定を一つの表へ確定する。PDFは1 GiBを開始案とする。以下の22 vCPU／12 GiB等の数量は0.5 GiB比較案に対応し、1 GiB採用時には再計算する。

| サービス | vCPU／GiB | min／maxインスタンス | 1インスタンスのconcurrency | サービス横断の制限                                          |
| -------- | --------- | -------------------- | -------------------------- | ----------------------------------------------------------- |
| return   | 1／0.5    | 0／4                 | 8                          | 利用者・要求・接続と結果を束縛。本文返却は一括              |
| business | 1／0.5    | 0／4                 | 8                          | 通常APIの実行余力をAI待ちから分離                           |
| writer   | 1／0.5    | 0／4                 | 8                          | DBの対象別禁止検査と期待版検査                              |
| send     | 1／0.5    | 0／4                 | 2                          | 全インスタンス・全世代を通じてAI2枠。患者要求の自動再送なし |
| safety   | 1／0.5    | 0／4                 | 8                          | 東京・大阪双方に配置。通常処理のAI枠と競合させない          |
| PDF      | 1／1      | 0／2                 | 1                          | 全体PDF1枠。通常APIと分離                                   |

大阪の待機業務5サービスは配備済みでも業務開放を無効にし、min0とする。safetyは待機扱いにせず平常時から両地域で耐久処理する。min0は料金最適化の開始案で、コールド起動を除外して性能合格にしない。returnまたはsafetyのmin1変更は、起動時間が既存p95や正常時2秒目標を満たさない場合に追加費用とともに比較する。

東京で全サービスがmaxに達した設定上の合計は22インスタンス・22 vCPU・12 GiB。大阪を同規模で動かす場合も同じ。これは実プロジェクトのquotaでも厳密な資源上限でもない。revision切替時の旧新重複を2倍で計画すると地域当たり44 vCPU・24 GiBが確認対象となるが、一時超過を含む実割当は別に確認する。

Direct VPC用サブネットの比較開始値は各地域／環境に専用/24。22インスタンスの新旧重複で、公式の2倍IP消費を掛けた88アドレスを起点とし、他資源・予約・一時超過の余裕を確認する。/24なら必ず足りるという保証ではない。実CIDRの衝突確認前に作成しない。

増設検討の契機は、通常APIのp95が2秒を超える、生成要求の待機＋外部実行＋結果検証＋返却がサーバー目標55秒・画面待機60秒の予算内に収まる見込みを失う、またはquota・IP・共有枠の使用率が80%に達する場合。受付判断も開始可能時刻だけでなく返却までの残時間で判定する。安全異常は増設で解消せず閉鎖する。枠不足や残時間不足では受付前に拒否して入力を保持し、受付済み要求の元期限を延長しない。まずDB待ち・AI待ち・CPU・メモリー・接続待ちを分け、必要な役割だけmax4→8等を比較する。AI2枠／PDF1枠はインスタンス増加で自動増加させない。

開始できることだけで60秒の応答条件に合格とはしない。受付判断では待機・外部実行・結果検証・返却までの残時間を評価し、AI待機45秒・サーバー目標55秒・画面待機60秒・要求終端5分の既存配分を維持する。

残時間の推定に必要な待ち行列年齢・起動・外部応答・検証／返却時間の測定と判定式は未確定。55秒／60秒の起算・計測範囲を元要求へ対応付け、受付後に計測を再起算しない。要求終端5分を返却目標の延長として使わない。

### 共有Slotの取得・解放・再割当

Cloud Runのinstance数／concurrencyは入口の並列処理設定であり、全体AI2枠／PDF1枠とは別である。共有枠は要求台帳のSlotと期限付きリース・実行世代で管理する方針を継承する。SlotId・OperationId・AttemptId・所有世代・状態版・証拠参照を対応付け、旧新revision・多instance・地域切替・重複配送を同じ全体枠へ含める。正本配置と原子的取得／更新／解放の具体方式は未確定。

| 状況                                             | 解放・再割当の判定条件                                                                                                                                                      |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| リース失効・通信断・ローカルtimeout・要求5分終端 | それだけでは解放しない。外部処理が継続中または成否不明なら占有相当を維持する                                                                                                |
| 未送信を証明できる試行                           | 未送信の証拠に加え、全旧実行者・旧許可が今後も送出できない証拠を確認して解放を評価する                                                                                      |
| 送信済み／送信の可能性あり                       | 当該AttemptIdの外部処理終了を信頼できる証拠で確認し、旧試行の再送・再実行も排除した場合のみ並列Slotの解放を評価する。取消し要求受理・socket切断・画面の終端表示だけでは不足 |
| 解放条件成立後                                   | Slotの正本で状態版・所有世代・証拠を照合し、一回だけ原子的に解放／新規割当する。古い所有者の復帰や重複配送で二重取得させない                                                |

AIが2件実行中に片方のリースが切れても、その外部処理が継続中／終了不明なら3件目を開始しない。開始した場合は全体2枠の条件に不合格。PDF1枠にも同じ判定を適用する。外部終了の確認手段と旧実行者の強制排除は未成立のため、条件を記載しただけで再割当可能とはしない。

並列Slotの解放と、消費回数・費用予約の精算を分ける。外部終了を確認しても消費／予算を自動返却せず、既存の課金証拠と重複精算防止条件を別に適用する。空きが確認できない場合は占有相当を維持し、新規生成は入力保持して拒否する。未確認の自動再送で空きを作らない。

公開前に地域別CPU／メモリーquota、Direct VPC接続上限・IP、Tasks配送・同時数、Firestore操作と競合、AI提供元のRPM／TPM、LB／NEG・NAT割当を実アカウントで取得する。使用率80%警報と増枠要否を記録する。公開資料の上限と実アカウントの割当を混同しない。

## 4. 利用者別停止の手順と成立しないケース

停止対象はAccountIdと、削除／同意等の対象・目的・版に束縛する。操作ID・実行世代・試行ID・最初の依頼時刻・元期限を保持する。

### 停止基準イベントと正常時2秒の区別

[停止境界の回答B](../../plans/patient-support-app-shared-gate-stop-boundary-questions.md)に基づき、外部AI送信と患者返却の新規本文引渡しは、対象の停止意図保存時点から禁止する。t0から保存までに限り、健全な現行世代による新規引渡しは他の許可条件を満たせば許容する。障害中に復帰した旧実行者の新規作用はD-02で拒否する。

| イベント／状態              | 既存定義と適用範囲                                                                                 |
| --------------------------- | -------------------------------------------------------------------------------------------------- |
| HTTP到達・本人／対象確認    | 別時刻で記録する。未確認要求だけで他人を停止しない                                                 |
| t0                          | 本人・対象確認済み請求の制御到達・送信順序調整開始。正常時2秒の起算点。t0前の滞留も別計測する      |
| StopRequested／停止意図保存 | 送信・返却の新規本文引渡しを禁止する境界。停止適用を進め、全旧経路の作用不能は別途証明する         |
| durableReceived             | 両地域に同一操作の受信記録が耐久保存された状態。停止適用完了とは別                                 |
| 業務DB禁止更新のcommit      | W-01の保存判定境界。これより前の保存確定は許容、後の保存確定は拒否。送信／返却の境界には流用しない |
| Blocked                     | 必要な業務禁止・二地域記録・対象に作用可能な全経路の停止証拠がそろった場合のみ確定                 |
| Accepted                    | 停止・耐久保護等の既存受付条件を満たした削除等の受付確定。物理消去完了ではない                     |

これらは単一の順番で必ず成功するものではなく、部分成功や応答喪失はPendingで照合する。正常時の2秒目標は既存配分案のt0からAccepted応答までで、障害時一律の上限ではない。t0から停止意図保存までの新規本文引渡しの合否は、回答Bを反映したSG-13で判定する。Blocked確認を後ろへ遅らせて古い許可の送出を許容する解決は採らない。

### 停止適用と表示の条件

1. 確認済み停止意図を保持し、新しい許可を拒否する。両地域への記録途中・応答喪失はPendingとして照合する。
2. writerが業務DBの禁止状態を適用する。W-01に従い、この更新前に確定した保存は停止前扱い、更新後の保存は拒否する。
3. 共通send／returnの対象Uについて、待機・予約・実行者・接続を列挙し、古い許可を拒否する。正常なVは対象混同なく継続させる。
4. 停止意図保存と、実本文引渡し開始の因果順序を送信・返却別に確認する。開始済み同一送信／返却の完了はD-01の例外に限定し、新規返却・再接続は拒否する。後続保存の可否はW-01の業務DB禁止commit境界で判定し、送信・返却の開始境界と混同しない。
5. 全経路の停止証拠、業務禁止、二地域の同一操作の耐久記録がそろった場合のみBlocked／Acceptedへ進む。停止時点をこの確認時刻へ移し替えて古い新規作用を許容しない。

画面の未確定・耐久受付済み・停止適用待ち・停止適用済みを区別する。停止意図保存・durableReceived・2秒経過だけでは「停止済み」と表示しない。停止適用済みの表示には対応する対象・操作・版のBlocked証拠、受付確定の表示にはAcceptedの条件を要求する。API項目・表示文言・応答喪失後の同一操作ID照会の詳細対応は未確定。消去完了表示へ流用しない。

### 具体的な反例と候補の判定

| 候補制御                      | 故障時の順序                                                                          | 判定                                                               |
| ----------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 送信直前にFirestoreを再確認   | U許可確認→プロセス休止→U停止意図／禁止更新→旧プロセス復帰→本文引渡し                  | PG-01不成立。再確認回数を増やしても最後の確認後の隙間が残る        |
| DB上の所有者リースと世代      | 旧所有者休止→リース失効／新所有者→旧所有者がローカル許可で送出                        | PG-02不成立。期限切れは旧socketの作用不能証拠ではない              |
| 利用者別actor・mutex          | 停止処理と送信処理を一つのactorで順序化しても、送出直前休止中に別経路で停止意図を受領 | 正常時の競合削減候補に留まる。停止処理の順番を遅らせて合格にしない |
| Cloud Run max1・timeout       | 旧revisionまたは処理継続中のcontainerが残る                                           | 全旧実行者排除の証拠に使えない                                     |
| VM停止・IAM変更・firewall変更 | 変更要求後、停止完了／伝播前または既存接続で旧主体が送出                              | 単独では不成立。共有VM全体停止ではU停止／V継続も満たさない         |

必要な追加機構は、対象別禁止の適用と実本文引渡しを同じ強制境界で順序付け、旧所有者・既存接続・再作成経路にも強制できる最終フェンスである。アプリ内直列化・DBトランザクション・管理APIの組合せについて、その境界を提供する公式保証は今回確認できていない。独自OS制御や別proxyを置く場合も、その最後の本文引渡しまで同じ検証が必要となる。

これはS1／S2の現在の制御案を採用できないという結論であり、あらゆる製品・実装についての一般的不可能証明ではない。遅延した旧実行者の送信を許容する仕様変更は行わない。新規質問で安全条件の承認を求める前に、成立根拠のある機構が見つかるかを技術側で判断する。

## 5. 二地域記録・復旧・切戻しの具体手順

東京／大阪の各安全記録には操作ID・対象・単調な対象版・禁止内容・元期限・記録内容のdigestを対応付ける。両地域の同一操作・同一内容が耐久保存された証拠と、各操作の確定結果を照合する。片方へのwrite成功や最大連番だけで二地域末尾の完全性を推定しない。両DBを一つのFirestoreトランザクションにはできない前提で、部分成功をPendingとして再照合する設計である。

| 状況                 | 手順・再開条件                                                                                                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 東京喪失             | 大阪の独立受付・メールを含む受信IDと未確定操作を棚卸し。大阪で障害前から利用可能な一般データ基準点＋更新／削除記録を隔離復元。東京の旧send／return・資格・経路の作用不能を確認する |
| 大阪喪失             | 東京側でも二地域確定と独立保護を満たせないため新規業務を開放しない。大阪の同一障害範囲内にコピーを増やして独立保護復旧としない                                                     |
| 地域間分断           | 両地域とも単独確定・単独昇格を禁止。片側で受けた禁止意図は保持して拒否へ反映。未到達の旧主体まで停止したとは宣言しない                                                             |
| 両地域復旧後         | 操作ID・内容・確定点・片側のみの意図・新着を照合。一般データの参照関係・現在の安全状態・削除期限を再適用し、実行世代を新しくする。古いdiskや一般backupの許可状態を正本にしない     |
| 大阪から東京へ切戻し | 業務を閉鎖し同じ旧主体排除・差分照合・隔離復元・受入を実施。逆同期で削除や同意撤回を復活させない。別担当が新着差分まで確認して一括開放                                             |

東京が使えず大阪だけが残る間は、D-04により停止継続を許容し、翌営業日着手・着手後24時間の未達を記録する。単独大阪でサービスを再開する手順ではない。独立保護を国内の元の2地域で再び確認できるまで閉鎖する。

### 分断時に閉鎖を強制するための残条件

| 確認対象                         | 定義済みの方針                                                                   | 未確定／未成立の部分                                                                                                 |
| -------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 各稼働ゲートの観測               | 必要な安全状態が確認不能なら新しい許可を発行しない。片側Accepted・単独昇格を禁止 | 東京／大阪の各send・returnが何を観測して閉じるか、依存照会の期限・欠測・遅延の扱い                                   |
| 分断検知前／最終確認後の休止復帰 | 古い許可による停止後の新規引渡しを許さない                                       | 最後の確認後から検知／強制遮断までの隙間を、実送出部品で排除する仕組み。heartbeat・短TTLの導入だけで保証済みにしない |
| 既存接続・proxy・旧revision      | 既存socket・旧URL・全旧実行者も作用不能の証拠対象                                | 新規接続の拒否だけでなく、保持済み本文・keep-alive・再作成からの新規作用を強制排除する手段                           |
| 対象別と全体閉鎖                 | 正常時のU個別停止とV継続、対象不明／共通制御故障時の全体閉鎖                     | 対象分離と全体閉鎖を全実行者へ強制できる機構。閉鎖方針やPending表示だけを成功証拠にしない                            |

全経路の登録一覧にはサービス・revision・起動ID・資格・URL・接続・再作成経路を対応付ける。停止Ack・旧経路拒否・実行者終了・本文引渡しの因果証拠を、[既存証拠仕様](gate-evidence-and-cutover.md)に従って取得する。自己申告の登録一覧や一度の拒否だけでは完全性を証明しない。実取得・完全性・旧主体への強制力は未実証で、これらが不明なら新版開放を保留する。

一般データは障害前の復元可能時点から4時間以内かを確認し、確定済み安全変更は無損失で照合する。Firestore標準backupを東京喪失後に大阪へ直接restoreする計画は使わない。鍵・資格・artifact・設定・受信経路も東京依存なく取得できるか確認する。削除7日・backup35日・追跡180日の既存起算を復旧で延ばさない。

## 6. 停止時間と実証する行列

計画停止時間は、入口閉鎖＋開始済み／unknown試行の分類＋旧主体の作用不能確認＋新版配備／実環境確認＋新着照合／別担当開放の直列部分で積算する。並行作業を単純加算せず依存関係を記録する。公開前受入は原則停止窓より前、公開後15分監視は開放後に計測する。旧主体の確認不能を一定時間経過だけで完了にしないため、現時点で停止時間の有限上限や推奨停止窓は算出できない。

| 検証ID | 注入・確認                                                                           | 必須証拠と判定                                                                                                                   |
| ------ | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| SG-01  | Uの要求へVの対象・結果・socket・PDF参照を混入                                        | 全組合せを拒否、正しいVは継続。本文を検証ログに保存しない                                                                        |
| SG-02  | send／returnの最終確認後・引渡し前で休止しU停止後に復帰                              | 停止後の新規本文引渡し0。未知は合格にしない。現制御案では反例が残る                                                              |
| SG-03  | 停止前に実開始した同一作用と、未開始予約を混在                                       | 前者の継続と後者の拒否を試行ID・因果順序で区別                                                                                   |
| SG-04  | 台帳分断・旧世代・リース失効・旧プロセス復帰                                         | 旧経路から送信／返却不可、新しい所有者だけで証明しない                                                                           |
| SG-05  | 既存keep-alive・proxy保持本文・再接続                                                | G-01の最終境界を特定し新規返却を排除。returnログのみでは合格不可                                                                 |

SG-02／03は停止意図保存を基準に期待順序を固定する。保存前に実開始した同一作用のみ完了を許容し、未開始の予約・許可や再接続からの新規引渡しは保存以降拒否する。SG-04／10は第5節の観測前・観測後・既存接続の各区間を含め、閉鎖通知の受領と実作用不能を別観測にする。

SG-02〜05は送信と返却を別ケースとし、write呼出し・OS引渡し・proxy・受信の観測を混同しない。SG-11の比率30／20／20／10／10／10%で各操作200件を満たすには、総数は少なくとも2,000件となる。公開前受入の6 API各100件＝600件とAI/PDF各10試行＝20試行は、この負荷試験とは別の集合で、切替時追加確認も別計上する。

机上反例の評価までを今回実施した。実故障注入・負荷・復元試験は未実施。後続資材は旧Canaryの1800件／60試行・canaryReconciledを改修し、検証ID・構成／設定digest・操作／試行／実行者／接続ID・順序証拠・unknown・判断者を出力する必要がある。既存artifactを書き換えて新方式成功扱いにしない。

## 7. 価格確認と費用判断

料金と数量は[費用正本第8節](../infrastructure-design/cost-estimate-100-consultations.md)へまとめる。S1の共通send＋returnの活動量を40,000／80,000／160,000 instance秒とする感度では、無料枠前の実行費は約1.05／2.22／4.44 USD／30日。CPU・メモリー・要求だけの額であり、全体費用ではない。常時待機min1は1サービス当たり無負荷月で約9.72 USDが比較基準になる。これらは稼働量の仮定からの計算で、容量達成・最終フェンスの実現費を含む完成見積りではない。

S1の検証優先を提案するが、構成採用・予算上限・許容停止時間の承認を今回は求めない。最終作用を強制できる機構と費用への追加を特定してから採用資料を確定する。旧VM単価例・旧比較小計を採用予算に使わない。

## 11. 質問票回答の反映とS1の成立判定（2026-11-18）

[回答票](../../plans/patient-support-app-shared-gate-resolution-questions.md)の質問7〜14を確認した。質問7は既存試験の適用範囲を確認してからBの計測設計へ進み、質問8は既存の復旧手順を採用根拠として参照し、足りない証拠・工数を具体化した。9はA、10〜14はB。回答間に矛盾はない。1〜6の追加回答は不要。

### 質問9：停止依頼の応答を受け取れなかった場合

同じ操作IDで本人・対象を再確認し、状態を自動照会する。手動の「状態を確認」を同じ照会に接続し、進行中の照会は合流させる。設計初期値は即時、その後2・4・8・16秒間隔で最長30秒。終端・認証切れ・画面離脱で自動照会を止める。画面を開き直したら再認証に従って同じIDの状態を照会する。操作ID単独では照会を許さず、患者情報や認証情報をURLや画面の永続ストレージに保存しない。

表示は「受付結果を確認できていません」「受付済み」「停止適用待ち」「停止済み」を証拠に応じて分ける。古い応答で表示を後退させない。手動確認失敗や自動照会打切りで状態を進めない。本文業務を自動再送せず、停止依頼を再提示する場合も同じIDで照合する。受入ケースは初回応答喪失、片側記録、古い応答の逆順、離脱・再認証、手動と自動の同時操作、停止適用証拠の欠測。

### 質問10：t0から意図保存までの扱い

回答Bにより、外部AI送信・患者返却とも停止意図保存から新規本文引渡しを禁止する。SG-13では経路別に、t0 → 初回本文引渡し → 意図保存の順を観測した場合、健全な現行世代で他の許可条件を満たすものを許容する。意図保存以降の初回開始は拒否する。意図保存前に実開始した同一作用の完了はD-01の範囲で許容する。障害中に復帰した旧実行者の新規作用はD-02で拒否する。t0は正常時2秒の計測起点として扱う。停止意図保存、最終引渡し開始および実行世代を因果証拠で照合し、順序不明は保留する。最終引渡しでの強制機構と実証は引き続き未成立。

### 質問11〜13：本文の最終引渡しと分断

- 送信はsend → HTTP/TLS → OS送信バッファ → 構成に応じたネットワーク中継 → 固定AI宛先。コンテナのwrite、socket受付、制御可能な送出点の先頭本文イベント、管理下の合成受信先の初回本文受領を別記録とする。TLS recordやTCP ACKだけでどの試行の本文が開始したかは確定しない。
- 返却はreturn → コンテナHTTP → Cloud Runの管理プロキシ／TLS経路 → 外部LB（構成による）→ 患者。通常取得・AI結果・PDFを個別に観測する。コンテナのfinishと患者側初回本文の間に管理経路があり、その間で保持された未開始本文の排除を既存仕様から証明できない。[Cloud Runコンテナ契約](https://docs.cloud.google.com/run/docs/container-contract)・[serverless NEG](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts)
- SG-02／03の候補は、対象・世代・試行・接続を検査する唯一の最終送出部品に停止受付と初回本文引渡しを集約し、同じ順序で強制する構成。開始済みの接続は同一試行の残りのみ許可し、再接続は新規判定。Uの予約中・確認後休止・下流保持の各点で停止後に復帰させ、Vを同時実行する。停止と最終本文の因果関係は操作・試行・接続IDと最終部品の順序番号、合成受信ログで追跡する。送出部品内部の確認と引渡しが分離される場合も休止を注入する。候補構成の強制力は未証明。
- 各地域は対象版、稼働世代、両地域の同一操作確定点、依存の応答と照会IDを照合する。欠測・異なる照会ID・旧世代・版の後退・期限超過を拒否する。照会期限は開始時の残予算と計測した依存遅延から決め、期限あり／短TTLは観測後に閉じる補助手段とする。共通制御故障または対象不明なら全体閉鎖。片側で受けた意図は保持し、単独Accepted・昇格を禁止。
- SG-04／07／10では、両地域で照会応答直後から次の観測までを含め、分断前の許可で最終部品が開始できるかを検証する。別主体が受けた停止を知れない最終部品は、正常時と分断時を区別できず、古い権限で開始できる。照会の高速化では区間は消えない。最終部品自身が停止と開始を排他的に順序付け、到達不能中の旧部品が新規開始できないことを示せない限り、PG-01／02は未成立で公開を保留する。

### 質問14：旧経路の棚卸しと排除

期待集合（IaC・配備履歴・再作成設定）と観測集合（両地域のクラウド構成、LB／NEG／DNS、サービス・revision・tag・資格／権限、キュー、egress、DB・Storage経路、接続）を独立に取得し、構成世代と取得時点を固定する。差集合、収集エラー、対象外の根拠、開放直前までの差分を別担当が照合する。入口は旧URL・直接経路の拒否、処理は旧資格／世代および再作成の拒否、既存接続と本文保持は最終送出部品で新規開始不能を確認する。SG-04〜06で既存接続、再接続、旧主体再作成、資格変更反映中、棚卸しの欠落を含める。入口の拒否記録と送出不能の証拠を対応付け、経路不明・照合漏れ・未観測は開放保留。

### 質問5・6：Slotの正本候補と解放

同時に書ける正本を1つに限定するFirestore台帳を比較候補とする。取得・終了証拠参照の確定・解放／再割当はそれぞれ同一DB内でSlotId、OperationId、AttemptId、世代、状態版を条件に更新する。外部作用は再試行され得るトランザクション外で扱う。応答喪失時は同じ試行を照合し、再配送で送出を重ねない。地域切替は旧書込・旧送出排除と二地域照合を前提に、未確定Slotを占有のまま移す。両DBにまたがる原子性、台帳不通時の継続受付、外部送出の原子性はこの候補から導けない。[Firestoreのトランザクション分離](https://firebase.google.com/docs/firestore/transaction-data-contention)

同期のResponses API（store: false）では、受信できた終端応答を当該AttemptIdへ対応付け、旧試行の再送を排除した場合に解放する。同期接続を閉じて取り消す手順はあるが、応答喪失時に当該試行の外部処理が終了したことを取得する手段は確認できていない。cancel APIはbackground専用で、backgroundは一時保存を伴う。現行条件では終了不明の枠を占有し続け、AIが2枠とも未知なら新規生成を拒否する。PDFは試行に対応する実行環境の終了と成果物／キュー／資格からの再実行排除を揃える。SG-14／15では発行元・試行の一致を検査し、証拠重複・逆順・旧世代の競合で解放は一度だけとする。[OpenAI DocsのBackground mode](https://developers.openai.com/api/docs/guides/background)・[Cancel API](https://developers.openai.com/api/reference/resources/responses/methods/cancel)

### 質問7：前回検証から使える証拠と受付判定

[実HTTP結果](../code/http-validation-summary.md)の38件と[ゲート検証結果](../code/gate-preparation-summary.md)の43件・調査22行は、観測点と反例の根拠に使う。構成別の実クラウド経路時間・メモリーのピーク値・quota・IPの採用値を決める計測は確認できないためBを適用する。

元要求IDに初回時刻と締切を固定する。受付時点の経過時間に、残待機・コールド起動・処理／外部実行・検証・サーバー返却の推定時間と誤差余裕を加え、55秒以内であることを確認する。別に同じ元要求からの画面側経過と受信・描画の余裕を含めて60秒以内、AI待機45秒以内、元要求終端5分以内を確認する。重なる工程はクリティカルパスで見積もる。地域・役割・暖機状態・負荷・版構成別の実測エンドツーエンド上位分位と留保データの過小推定幅を使う。推定の根拠不足、計測欠落、枠不明、期限不足では入力を保持して新規生成を拒否し、元期限を延長しない。

SG-11の20人、立上げ5分＋定常30分、各操作200件以上の同一負荷で0.5／1 GiB、min0／min1、コールド・暖機、旧新資源混在時を比較する。混在試験で旧版業務の開放は行わない。起動時間、キュー年齢、区間別遅延、成功率、RSSと一時ファイル、OOM、リージョンquota、サブネットIP（旧新・縮退中を含む）を構成digestに対応付ける。予測誤差と受付後の期限超過率を記録し、採用値は実環境判定まで保留する。[Cloud Run quotas](https://docs.cloud.google.com/run/quotas)・[Direct VPC IP割当](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc#ip_address_allocation)

### 質問8：復旧・一括切替の証拠と積算

第5・6節を基礎に、SG-09では両地域の操作ID・版・digest・元期限・確定結果を突合し、片側成功を保持してPendingとする。SG-10では東京に依存しない鍵・資格・artifact・設定・受信系の取得を実演し、一般データの基準点（RPO4時間）と新着／削除の順序を照合する。復元時に停止・撤回・削除を再適用し、期限を延長しない。SG-12では閉鎖時点と照合終点の間の新着、未確定操作、旧主体排除、独立した二地域の保護、6 APIとAI/PDFの実環境確認を証拠束にし、別担当が照合して一括開放する。公開前受入の通常600件・AI/PDF20試行、切替時確認、開放後最低15分の毎分監視を区別する。欠測や矛盾は開放保留、開放後なら停止。

停止時間は入口閉鎖から別担当の開放まで。閉鎖後に一般復元と鍵・成果物検証は依存がなければ並行し、旧主体排除・新着最終照合・実環境確認・別担当判断は前提が揃った順に行う。費用は並行稼働も含め、両地域の資源存続時間×地域SKU、DB／復元と通信量、試験・監視・再試行、最終送出部品・接続監視、鍵／資格／artifact、担当者工数を積算する。既存の[費用正本](../infrastructure-design/cost-estimate-100-consultations.md)の仮定を引き継ぎ、最終フェンスの構成、実測時間、地域枠と費目が未確定のため停止上限と総額は保留。

適用評価は第9節の規則別評価を継承。RESILIENCY-04・08〜13は未適合を継続。部分PBTの実行は設計文書のみのためN/A。純粋な受付判定・集計・証拠の往復変換を後続検証へ引き継ぐ。セキュリティ拡張は無効のため適用省略。
