## AC-01：共通ゲート内で利用者別に認可・停止する（2026-11-15更新）

ユーザーが費用を理由に共通ゲートを選択。[共通ゲート設計](shared-gate-design.md)を現行正本とする。送信・返却の各役割の実行基盤を複数利用者で共有し、利用者専用VMを前提にする比較を取りやめる。

以前の回答1Bで求めた利用者別隔離は、共通基盤内の本人・対象・同意・期限・停止・接続・結果の分離として維持する。Uだけを停止して正常なVを継続できる条件を緩めたものではない。共有制御故障や影響範囲不明なら全体を閉鎖するが、全体停止だけで個別停止の要件を満たしたとは扱わない。

| 構成 | 現行の扱い |
| --- | --- |
| 共通送信ゲート・共通返却ゲート | 採用する設計方針。製品・台数・安全性の成立は別途確定 |
| 利用者ごとの専用VM | 現行の設計・費用算定の前提から除外。過去比較として保持 |
| 共有基盤全体を止めるだけで個別停止できない方式 | 現行の利用者別停止条件を満たさない。共通化の指示だけで採用可にしない |

最終確認と実引渡しの競合、共有proxy、旧実行者再作成は引き続き検証対象。共通化だけでPG-01/02が成立するとはしない。登録100人・同時20人の容量は、共通poolの負荷試験と台数・上下限の確定で満たす。登録人数ぶんのVMは要求しない。

回答原文は「A　担当は決定済み、営業日は設計に記載済み」。担当未決定として再質問しない。[非機能要件](../nfr-requirements/nfr-requirements.md)のNF-12と詳細1から、寄り添いチーム・平日10:00〜17:00日本時間・メール連絡を継承する。翌営業日着手、着手から24時間以内の大規模復旧目標、復旧実行と別担当による再開確認を維持する。

実名・メールアドレスをこの文書に転記しない。通知先への実配送、休日カレンダー、採用構成に必要なVM保守権限・作業分担の適合は公開前の確認項目として残す。担当決定済みの回答だけで通知経路や新構成の保守検証が済んだとは扱わない。

## AC-03：外部サービスの追加指定なし

既契約・禁止先等の追加指定はない。既存の処理地域・保持・削除・認証条件に対する根拠、不足条件、費用を技術側が提示した後に採否を判断する。既存候補を取り消したり、未選定の提供元を自動採用したりしない。

## 残る作業と順序

1. 共通ゲート内の利用者別制御と最終作用の遮断を両立する具体構成を検討し、故障モデル・作用境界・対象別停止の証拠をそろえる。
2. 候補の実通信・DB権限表、二地域保護、受信境界と復旧手順を具体化する。
3. 一括切替の停止時間、通常月・追加試験・隔離資源の費用、外部サービス条件と運用負担を提示する。
4. 構成採用・停止時間・予算と具体的なコード変更計画をレビューし、承認された範囲で資材を改修・検証する。実クラウド・課金・外部送信の許可は別途具体化する。

現時点の追加質問はない。PG-01〜04・二地域復旧・費用等の技術課題は継続する。
