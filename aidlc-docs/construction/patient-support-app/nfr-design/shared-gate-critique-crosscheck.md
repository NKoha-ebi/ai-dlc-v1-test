## 1. 結論

批評の主要な未成立指摘は既存資料とも一致する。ただし、2秒の起算・状態遷移、共有枠の保存先と管理方針、旧経路排除の証拠項目は他文書に既に記載があり、「設計がない」と「設計はあるが詳細／実証が不足」を分ける必要がある。

## 4. 現時点で説明できる時系列と不足

以下は既存規定の整理であり、新しい保証境界の採用ではない。

1. HTTP到達・本人確認・対象確認を別時刻として記録する。未確認要求だけで他人を停止しない。
2. t0は確認済み請求の制御到達・送信順序調整開始。正常時2秒の計測をここから開始し、t0前の滞留も別計測する。
3. StopRequested／停止意図保存、両地域の同一操作の耐久記録、業務DB禁止適用、最終ゲート停止通知・静止証拠をそれぞれ記録する。両地域のdurableReceivedは受付記録の保護であり、停止完了ではない。これらの処理は常に単一の固定順で成功するとは限らず、片側成功・応答喪失はPendingで照合する。
4. Blockedは必要な業務禁止・二地域記録・全対象経路の停止証拠がそろった場合だけ。Acceptedはその条件を満たした削除等の受付確定で、物理消去完了ではない。正常時の旧配分案はt0からAccepted応答まで約2秒を目指す。障害時にはその上限を保証しない。
5. DB保存はW-01の禁止更新commitとの順序で判定する。外部送信と本文返却はG-01の実本文引渡し開始との順序で判定する。Blockedを後から確認できたという理由で、その前の古い許可による新規送出を許す境界へ変更しない。

**送信側**ではsendが本文の最終引渡しを担う役割だが、停止の比較イベントとsocketへの引渡しの排他が未成立。**返却側**ではreturnからLB／proxyを経る実経路のどの引渡しが最終境界になるかも未確定。このため、各経路について「この瞬間から必ず全旧処理が拒否する」と実装保証を伴って示せる時系列はまだ作れない。

画面には既存契約として未確定・耐久受付済み・停止適用待ち・停止適用済みを区別する規定がある。ただしAPI状態からの表示条件・文言・応答喪失時の再照会を一つの画面契約に対応付けた定義は不足している。2秒経過、停止意図保存、durableReceivedだけを理由に「停止済み」と表示できる規定はない。

## 6. U2・U6の追跡条件の補足

ユーザーの指摘を受け、停止境界を技術側の自由選択にしないことと、成否不明時の再割当条件を明確にした。以下は解決すべき契約と検証条件であり、強制機構の成立や試験成功の宣言ではない。

| 対象ケース | 確認・判定条件 | 現在の状態 |
| --- | --- | --- |
| U2：t0→本文引渡し開始→停止意図保存 | 送信・返却を別々に、D-01／02、W-01〜03、G-01〜04の適用イベント・例外・優先順位へ対応付ける。2秒の起算定義だけで合格／不合格を決めない | 既存文書でこの順序の合否を一意に決められるかの照合が必要。決め切れなければ両解釈の合否差・利用者影響を示す |
| U6：AIが2件実行中→片方のリース失効→旧外部処理が継続 | 外部処理が継続中または終了不明なら、その1枠は占有相当を維持する。この間に3件目を開始すれば全体2枠の条件に不合格 | リース失効を解放証拠にしない条件を明記。提供元側の終了確認手段は未確定 |
| U6：予約後に未送信のまま停止した可能性 | 未送信の証明に加え、全旧実行者・旧許可から今後も送出できない証拠がそろう場合のみSlot解放を評価する。ローカル記録の未送信表示だけでは不足 | 既存の未送信／旧送信者排除条件を継承。実証は未完了 |
| U6：送信後に応答喪失／取消し要求／通信断 | 対応するAttemptIdの外部処理終了を信頼できる証拠で確認し、旧試行の再送・再実行も排除した場合のみ並列Slot解放を評価する。取消し要求の受理・socket切断だけでは外部処理終了としない | 対応する提供元の終了証拠が得られない場合の解放は保留。要求終端5分も外部処理終了の証拠にはしない |

外部処理の終了を確認して並列Slotを解放できても、消費回数・予算予約を自動で返却する根拠にはならない。回数・費用の精算には既存の送信／課金証拠と重複精算防止条件を別に適用する。枠を維持して新規生成を拒否する場合は入力を保持し、未確認の自動再送で空きを作らない。

公開判断の最優先追跡対象は、停止の基準イベント、実本文を出す最後の部品、分断・旧接続・旧処理に対してその部品で遮断を強制する仕組みの3点とする。今回の補足を既存要件の緩和・境界の採用・実証済みへの変更とは扱わず、新たな承認は求めない。
