# 利用者別ゲート：具体構成・成立性レビュー

2026-11-14。[追加制約](gate-additional-constraint-decisions.md)の確認完了と具体化指示に基づく机上検討。D/W/G判断と[一括公開方式](beta-bulk-release.md)を維持する。

## 結論と今回進めた範囲

利用者別の最終送信・返却を専用実行単位へ分離する構成を具体化した。ただし、今回調べた仕様と構成では、停止と実ネットワーク引渡しの順序を保証するPG-01、および全旧経路の排除PG-02の両方を満たす採用可能な方式は確定できない。利用者別VM化だけでは解消しない。

以下は検証候補と反例・必要証拠のレビュー資料。配備可能な構成の完成、停止時間の測定、総費用の確定ではない。全体の公開採用・NFR設計完了・実装には進めない。利用者別隔離や停止境界を緩める決定はしない。

## 1. 対象と故障モデル

- 登録100人・同時20人・月100相談。利用者Uの停止で、正常な利用者Vの本文経路を止めずに済む隔離を構成の採用条件とする。共有制御の故障・対象不明では全体停止を維持する。
- プロセスは最終確認の直後を含む任意位置で休止・復帰し得る。VM停止要求、台帳更新、ネットワーク・管理制御面の応答は遅延・喪失し得る。既存接続、旧世代、待機系、再作成、設定違いも含める。
- 正常なOS・クラウド管理基盤の仕様に依存する設計。基盤侵害や管理者による意図的な不正変更まで保証しない。ただし通常業務資格からの再起動・別資格偽装・任意外部送信は許可しない構成を要する。
- G-01の開始点は最終経路からネットワークへの本文引渡し開始。DB予約・許可取得・write呼出しを開始に変更しない。D-01の停止前開始分の完了例外は維持する。
- 本人・対象確認後の既存t0、停止意図保存、経路への停止通知到達、最終停止適用、Acceptedは別イベント。停止適用時点を後ろへ定義し直して、古い許可による新規作用を許す解決は採らない。

## 2. 具体的な配置候補

以下のP2は比較のための設計案であり採用決定ではない。東京を主系、大阪を停止中の待機系とし、両地域の安全台帳が確認できる間だけ開放を検討する。

| 候補 | 最終経路と隔離 | 評価 |
| --- | --- | --- |
| P0：現在のCloud Run試作 | 共有実行環境で世代を再確認して送信・返却 | 既知反例が残る。現方式を採用しない |
| P1：共有ゲートVM | 全利用者の最終経路を同じVMへ集約し基盤停止 | AC-01の利用者別隔離に不適合。公開採用候補から除外 |
| P2：利用者別のゲートVM | Uの送信・返却をU専用VMで実行し、Uの全旧VMを基盤停止。VのVMは継続 | 隔離を設計できる方向だが、停止要求から基盤停止完了までの競合が残る。成立保留 |
| P3：同じVM内の利用者別プロセス・コンテナ | 対象プロセス、socket、送信経路を個別に停止 | OS側での停止と最終I/Oの排他根拠が別途必要。名前空間やプロセス分離だけでは解消しない。成立保留 |

### P2の経路と責務

静的UI・本文なし状態案内は共有のまま。業務処理からの本文は利用者Uの内部要求に限定し、U専用の最終ゲートへ渡す。最終ゲートはUの本人・対象・同意・版・期限・世代を検証し、外部送信または患者への一括返却を実施する。PDFも同じ返却経路を通す。

外部送信先の資格・宛先は固定する。任意URL、redirect、直接Storage配信、業務側からの患者本文返却を禁止する。UのゲートがVの本文・秘密を取得できない境界を必要とする。利用者別VMであっても、同じ広いDB資格を持たせればこの条件を満たさない。

本文返却に共有L7 proxyが本文を保持・送出する構成では、そのproxyも最終経路の検討対象となる。UのVM停止だけでproxyの後続送出を排除できるとはしない。TLSを利用者別ゲートで終端する経路も比較できるが、L4中継・送信bufferを含めG-01がどの引渡しを指すか確認が必要で、単なる「TLS透過」で合格にしない。

東京と大阪の同時開放は禁止。待機VMは停止中でも棚卸しし、起動には最新世代と別担当確認を要求する。自動修復・schedule・起動権限等の全再作成経路を把握する。二地域台帳は本文を持たず、ゲートVMのdisk・snapshotを安全変更の正本にしない。

## 3. 公式仕様の照合と反例

2026-11-14に公式資料を確認。以下の「推論」はサービスの保証ではなく、この要件への設計評価である。

| 確認した仕様 | 本設計への意味 |
| --- | --- |
| Compute Engineは停止中と停止完了TERMINATEDを区別し、停止完了後も明示起動等で再開できる | 停止API要求の受領は作用不能の証拠にならない。停止後状態と再起動禁止を別々に確認する。[ライフサイクル](https://docs.cloud.google.com/compute/docs/instances/instance-lifecycle) |
| 停止手順には終了処理と停止operationの完了待ちがある | 終了処理を省略しても、別の台帳上の停止と最終送信を原子化する仕様ではない、という推論。[停止手順](https://docs.cloud.google.com/compute/docs/instances/stop-start-instance) |
| IAMの変更には伝播時間がある | 失効API成功や一度の拒否試験を、全旧資格の即時失効の保証にしない。[IAM伝播](https://docs.cloud.google.com/iam/docs/access-change-propagation) |
| VPC firewallは接続状態を追跡し、許可済み接続の応答を扱う | 既存接続も含めた停止をルール更新だけで証明しない。[firewall仕様](https://docs.cloud.google.com/firewall/docs/firewalls) |
| Cloud Runの要求timeoutはコンテナ停止を意味しない | 応答timeoutだけで旧実行者の終了を証明しない。[timeout](https://docs.cloud.google.com/run/docs/configuring/request-timeout) |
| Application Load Balancerはクライアント側とbackend側の接続を分け、構成によりTLSを終端する | backend VMの停止だけで最後の患者向け本文経路を止めたと推論しない。[接続とTLS](https://docs.cloud.google.com/load-balancing/docs/https/request-distribution) |

### 机上の反例順序

以下は設計上許されてしまう順序の検討であり、今回クラウド・OS試験を実行した結果ではない。

| ID | 順序 | 判定と不足 |
| --- | --- | --- |
| F-01 | Uの旧実行者が許可確認→休止→制御側がUの停止意図を記録しVM停止を要求→停止完了前に旧実行者が復帰して新規本文を引渡し→VM停止完了 | P2だけではこの順序を排除できない。Pending表示や停止完了待ちで、その前の新規作用を正当化しない。PG-01未成立 |

F-01への必要条件は、停止操作と実際の最終引渡しを、休止・復帰しても破れない同じ排他領域で順序付けること、または停止後の古い許可を最終I/O側で拒否できること。DB再読込・短いlease・VM停止要求の追加だけではこの条件の説明にならない。外部AIへの予約を先に記録してもG-01を満たさない。

今回の公開仕様確認だけでは、その排他領域を実現する製品契約・実装を特定できていない。「どんな方式も不可能」という一般的証明は行っていない。採用候補を得るには、この点を先に解く必要がある。

## 5. 停止時間の積算

採用候補未確定・実測なしのため、現時点で「何分で安全停止・公開できる」という見積りは出せない。以下を同じ配備IDで計測し、許容停止時間は数値提示後に判断する既存回答を維持する。

計画停止の時間＝入口閉鎖＋開始済み／未知試行の分類＋旧主体排除の完了確認＋新版の起動・設定確認＋実環境受入＋新着差分照合・別担当開放判断。並列化できる処理は依存関係上の最長経路で積算し、全工程を無条件に並列としない。

旧主体排除は、対象となるU・全boot・proxy・待機系ごとに、要求から停止operation完了・状態確認・再作成禁止確認まで測る。段階的なbatch処理ならbatchごとの最遅値を合算する。管理面不通・未知結果は上限不明であり、安全停止完了時間を有限値として見積もらない。

公開前600件＋AI/PDF20試行は入口閉鎖前に終える。切替時の追加確認は停止時間に含め、件数と実AI課金を別計上する。公開後最低15分監視は全利用者への開放後であり、計画停止へ機械的に15分を加えない。異常再停止は別に測定する。通常時の安全制御2秒目標と計画停止時間を混同しない。

## 6. 費用数量と運用負担

費用正本は[月100相談の概算](../infrastructure-design/cost-estimate-100-consultations.md)。従来の47〜63 USD等は完成構成の総額ではなく、この候補を追加した最新見積りとして使わない。今回は確定見積りを作れる成立候補がないため、価格不明を0にせず数量と式を示す。

### P2を比較する場合の数量

1利用者・1地域に送信／返却を兼ねるVMを1台置く比較仮定。10 GiBのboot diskも単なる算術上の仮定で、容量・machine typeの採用値ではない。送信と返却を別VMにする場合は、該当資源をそれぞれ数える。

| 比較ケース（30日720時間） | VM稼働時間 | 常設diskの算術量 | 注意 |
| --- | --- | --- | --- |
| 登録100人の東京VMを常時稼働、大阪100台停止待機 | 東京72,000 VM時間、大阪の実起動時間は別加算 | 両地域200台×10 GiB＝2,000 GiB月 | 停止中のdiskは消えない。待機の稼働時間を実測で加算 |
| 東京で20人分を常時稼働、大阪100台停止待機、登録100人分のdiskは保持 | 東京14,400 VM時間＋追加起動分 | 同じ仮定なら2,000 GiB月 | 同時20人は常時20台という実利用予測ではない。起動待ちと認証・初回表示性能が未解決 |
| 対象利用時だけVMを起動・終了 | 利用・起動・監視・停止遅延ごとの時間合計 | 実在disk容量×残存時間を合計 | 月100相談から稼働時間を推測しない。旧主体確認前に枠を再利用しない |

月額＝東京VM時間×東京単価＋大阪VM時間×大阪単価＋地域別disk・snapshot・image＋LB／IP／proxy／NAT／DNS・通信＋Run／DB／安全台帳／backup・復元＋監視・ログ／秘密／CI＋外部AI・メール・domain－確認できた重複。運用工数は別欄にする。

感度として、東京VM単価が0.001 USD／時間増えるごとに、72,000 VM時間なら72 USD、14,400 VM時間なら14.40 USD増える。これは価格表ではない。総額未確定を示す算術例であり、東京・大阪の単価を仮定した予算ではない。

[公式VM料金入口](https://cloud.google.com/products/compute/pricing)と[disk料金](https://cloud.google.com/compute/disks-image-pricing)を確認。一般目的VMの地域別料金ページ取得はtimeoutとなり、東京・大阪の対象machine typeの確定単価は未取得。diskページも地域選択とSKUを固定した値として採用していない。既定表示の他地域料金を日本料金へ流用しない。停止後にもdisk等の残存資源には費用が発生するため、終了棚卸しが必要。[公式停止後の課金](https://docs.cloud.google.com/compute/docs/reference/rest/v1/instances/stop)。

追加試験費は、検証対象のVM数×試験・起動・停止待ち時間、disk等の存続、DB read/write/deleteと復元量、送信量、公開前600件・20試行、切替確認、公開後監視、再試行を別々に積算する。権利請求・同意変更での利用者別隔離試験には、最低でもU/Vの独立経路と旧世代を要するが、今回その有料実施時間や上限を承認済みとはしない。

### 運用で増える作業

担当決定済み、寄り添いチーム・平日10:00〜17:00日本時間・メール連絡を継承。担当の再回答は求めない。VM案ならOS image更新、patch検証、対象別資源・旧世代の棚卸し、証明書と秘密の更新、削除後disk／snapshotの消去確認、quota・起動失敗対応、停止operation不明時の照合が増える。実作業時間は未測定で、工数0とはしない。復旧担当と別の再開確認担当を維持する。

外部サービスの追加指定なしは、契約適合の確認を免除する決定ではない。AI・認証・メールの処理地域、保持・削除、実通知経路と費用は既存条件への根拠をそろえた後で採否を提示する。

## 7. 次に解く技術課題

最優先はF-01の排他領域・最終I/Oの実装根拠と、F-02の最終返却主体の確定。成立根拠が得られるまでは、VM・LB・NATを並べた資源作成や試験資材の大量改修を進めても採用可能性を上げたとは判断できない。

今回新しい業務方針の回答依頼はない。必要な技術調査を残したまま、構成や予算を承認するよう求めない。条件変更が必要と判明した場合は、元条件との差分と具体的な影響を提示して別途判断する。現在の条件は維持する。
