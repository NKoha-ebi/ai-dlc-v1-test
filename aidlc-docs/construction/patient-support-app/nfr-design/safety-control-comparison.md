## 3. 確定手順と判定責務

1. 独立した権利請求入口を両地域へ配置する。要求ID・最小参照・受信段階を記録し、本人未確認と本人確認済み意図を分ける。記録前切断も含め、到達し得る入口と未記録区間を追跡する。耐久化後の応答だけを見て受信完全性を証明しない。
2. 本人確認後、対象・目的・新制御世代・新規処理禁止を保護台帳へ保存する。両側の耐久確認を必要条件にする。タイムアウトは成功扱いせず要求IDで照合する。
3. 最終実行経路が書込・送信・返却を仲介する。業務経路には直接DB書込権限・外部API秘密を与えない。全作用を実行世代と対象版で照合し、古い世代・判定不能・期限切れは拒否する。
4. 実行中作用の順序を確定し、未開始作用を拒否できた証拠を保存して利用遮断を確定する。許可確認と実送出の間で停止する競合、既存接続、予約済み処理、遅延書込・返却を含む。許可トークンの短いTTLや直前再読込だけで2秒保証を成立済みにしない。
5. 利用遮断と独立耐久保護の両条件が揃ったときだけ削除等の受付確定を返す。最大2秒で順序を確定できない場合は新規作用を停止して保留表示。送出済みデータの取消と、その結果の保存・適用・表示拒否を区別する。
6. 地域喪失後は受信到達点、未処理要求、制御末尾、旧世代の実行不能、復元物の隔離を別担当が確認して開放する。東京なし・大阪なしを別試験にする。一般データの復元点と制御台帳の無損失を混同しない。

DBと外部HTTP送信を原子的にcommitできるとは仮定しない。判定後に停止した旧プロセスが再開して実送出できる構成は不合格。全最終作用を覆う排他・世代失効と実行機構の設計が共通の残課題であり、台帳の複製だけでは解消しない。

## 7. 最大2秒の判定・停止手順（次回レビュー案）

### 起算・状態・保証する対象

本人と対象を確認した権利請求が制御処理へ到達し、送信開始との順序調整を開始した時点をt0とする案。生のHTTP受信時刻・本人確認時刻・意図保存時刻・t0を別に残す。t0の直前に長時間待機させて2秒計測から除外しない。本人確認からt0までの遅延も監視し、速やかな利用停止に反する滞留は別途不合格とする。受信から全処理が2秒で完了するとの要件変更は行わない。

制御状態はOpen→StopRequested→Quiescing→Blocked→Accepted。PendingはStopRequested／Quiescingの未確定表示であり、Openへ戻す状態ではない。Acceptedは削除等の受付確定、物理消去完了とは区別する。自動再試行で期限起算を更新しない。

| t0からの設計上の配分 | 操作 | B |
| --- | --- | --- |
| 0〜0.3秒 | 新規処理禁止と世代更新 | 両台帳へ停止意図を記録。片側だけでもその側は拒否を維持 |
| 0.3〜1.0秒 | 最終実行者へ停止通知、未開始処理を取消 | 双方の停止意図・実行台帳を照合。片側未到達なら確定不可 |
| 1.0〜1.6秒 | 実行者と作用の静止確認 | 書込・送信・返却の各最終経路から静止証拠を収集。2地域記録に加え旧実行者排除の証拠が必要 |
| 1.6〜1.8秒 | Blockedと独立耐久保護を確定 | 両側の確定記録を確認。片側応答喪失は要求IDで照合 |
| 1.8〜2.0秒 | 応答と余裕 | 条件成立時のみAccepted、未成立はPending |

数値は未実測の配分目標であり、製品レイテンシ保証ではない。制御担当自身が停止した場合、タイマーも動かないため2秒の応答を保証できない。画面側の待機終了表示は補助で、サーバー側停止の証拠にはしない。

### 2秒時点で確定できない場合

動作中の制御経路では、新しい許可の発行・キュー取出し・対象結果の保存／返却を拒否し、Pendingを返す。既に送出した作用は送出済み／成否不明へ分類し、外部再送や遅延結果の利用を止める。既存接続の切断要求、処理取消、旧実行者の隔離を継続する。ただし、切断要求を出した事実だけで静止確認済みとはしない。

| 最終作用 | 必要な具体証拠 | 現候補で残る不足 |
| --- | --- | --- |
| DB書込 | 対象の禁止状態と同じ原子的境界で書込可否を判定し、遅延commitを拒否 | 制御用の2地域台帳と業務Firestoreは別DB。別々の再確認では原子性がない |
| 外部送信 | 送信仲介が停止後の送出を拒否し、旧接続・停止プロセスからの送出も実行不能 | DB世代更新はソケット送出を取り消さない。NAT・固定IP・IAM失効要求は2秒の実行遮断証拠ではない |
| 取得・画面返却 | 全返却とストリームを仲介し、旧経路から新規返却できないこと | 判定直後に止まったHTTP処理が後から再開し得る。取得済みデータの遠隔回収は対象外 |

必要な補強候補は、業務書込と禁止判定を同じDBトランザクションへ寄せる案、および送信／返却の全バイトを最終ゲートへ集約して静止確認する案。ただし後者のゲート自体の停止・復帰も検証対象であり、ゲートを追加しただけで解決しない。いずれも現在のB案の構成範囲と費用を変えるため、採用済みとはしない。

[Cloud Runの公式タイムアウト仕様](https://docs.cloud.google.com/run/docs/configuring/request-timeout)では、応答タイムアウト後もコンテナ内処理が継続し得る。Abort・504・短いリースのいずれも単独で遮断保証にはならない。

結論：B案は「2秒以内に保留判断する設計」と「保留時に全最終作用を停止できる保証」を分ける。前者の配分案は具体化したが、後者は未成立。Pendingを返せば合格とは判定しない。

## 8. B案の確定手順と地域喪失後の再開

### B：2地域確認台帳

具体化した正常手順は、両側Prepare保存→両保存結果を参照するDecision保存→両側のDecision保存確認後に確定応答、の順。要求IDと対象世代ごとに一意とし、Decisionには両Prepareの版と内容digestを対応付ける。片側Prepareだけで後から許可を出さない。各段階の再実行は同一要求を照合し、通信切断を失敗確定へ読み替えない。

地域喪失時、残存側のPrepare／Decisionはすべて保守的な拒否対象へ取り込む。確定応答済みの記録は正常手順なら残存側にも存在する一方、片側Decisionだけの要求が実際に確定済みだったかは判別できない場合がある。削除・撤回の意図を捨てず、曖昧な要求は保留する。新しい書込者への切替には、旧書込者が将来の作用を実行できない証拠と、新しい独立保護先が必要。連番やhashだけではどちらも成立しない。

| 障害 | B案の再開に必要な追加条件 | 現在の判定 |
| --- | --- | --- |
| 東京永久喪失 | 大阪台帳の全意図・未確定要求を反映。RPO4時間以内の一般復元点を取得し、別の独立保護先を用意して東京書込者を排除 | 復旧目標内の成立未確認 |
| 大阪永久喪失 | 東京台帳を保守的に照合し、独立保護先を再構成。旧書込者の作用不能を確認 | 業務主系が健全でも安全条件で停止し得る |
| 地域間分断 | 両側確定を停止。単独昇格しない | 安全な拒否は可能でも、分断が長期化すれば復旧目標未達 |
| 両地域喪失 | 今回の2地域案だけでは復元元・制御記録が不足 | 保証範囲外。単一地域喪失までの成立と混同しない |

### 復旧目標と照合する作業配分

翌営業日の対応着手をSとし、S＋24時間までの完了を評価する。自動検知・利用停止はSまで待たない。設計上の配分案はS＋1時間まで影響範囲確定、3時間まで復元元・制御末尾確認、9時間まで隔離復元、15時間まで受信／安全変更／削除反映の照合、19時間まで旧資格拒否・認証・業務試験、22時間まで別担当の開放確認、残り2時間を余裕とする。担当は既存の同一チーム内の復旧担当と別の再開確認担当で、実名・営業日・通知先は利用開始前に固定する。

この配分は作業量の仮定であり達成実証ではない。失われた地域の復帰待ち、新しい保護先の調達、受信区間不明、旧実行者隔離の証拠待ちが残れば時刻だけで開放しない。S＋24時間を超えれば復旧目標未達として記録し、方式へ戻る。現行B案にはその超過を防ぐ成立済み手段がない。

## 9. 権利請求の受信境界と照合

| 境界 | 記録・表示・復旧時の扱い |
| --- | --- |
| ブラウザーで送信操作、入口へ未到達 | クライアント操作IDを保持し、受信済みと表示しない。再提示は補助でありサーバー側の完全性証拠ではない |
| HTTP入口へ到達、独立記録へ未保存 | transportReceivedと呼ぶ。ここで地域を失うと要求の存在・対象を復旧側で知れない可能性がある。未受信だったと扱わない |
| 独立受信記録の保存完了 | durableReceived。受信ID・入口ID・入口世代・操作ID・受信時刻・最小対象参照・確認段階を保存。両側保存を条件とする |
| 本人・対象確認後、停止意図保存 | verifiedStopRequested。前節の2秒順序調整へ接続する。未確認要求だけで他人を停止しない |
| 遮断と独立保護を確定 | Accepted。削除等の元の期限起算を適用。応答喪失後も同じIDで状態確認し、受付を作り直さない |

本文・メールアドレス・生トークンを制御台帳へ複製しない。本人未確認の記録も無期限保持せず、保持対象と期限を既存保存契約へ対応付ける。アプリのtransportReceivedをdurableReceivedだけに狭める変更は採用しない。

入口は東京／大阪の専用受信経路に限定し、旧業務API・旧版URL・直接DB経路を一覧化して閉鎖する。各入口世代について、起動時・閉鎖時の記録、耐久到達点、操作IDと各受信IDの対応、未処理件数を照合する。IDは欠番の意味を区別できる採番方法とし、番号を発行しただけで受信内容が保存済みと判断しない。窓口メールは別の受信ID・元時刻・到達点で照合し、アプリの記録前欠落をメールで補完済みとはしない。

補強候補は、受信枠を独立保護してから要求内容を確定する2段階入口。ただし内容送信前後の断絶は残り、未完了枠の対象・意図を確認できなければ安全側で開放を保留する。入口で全受信を失われない記録へ結び付ける仕組みが未成立のまま、利用者が送信を繰り返せば完全になるとは説明しない。

再開判断では入口別の受信範囲を固定し、その範囲までの各要求を反映完了・本人確認待ち・処理保留へ分類する。対象不明の欠落区間があれば全体開放不可。対象が特定でき、他対象へ影響しない証拠がある場合だけ対象単位の停止を検討する。新着は新入口世代へ連続して引継ぎ、照合終了時刻で消えないよう別担当が差分確認する。

## 10. 設計検証の反例と結果

実装・クラウド試験ではなく、状態遷移の有限トレースと故障時点の紙上検証。全状態の網羅証明ではない。

| ID | 操作・故障の順序 | 判定と必要な修正 |
| --- | --- | --- |
| V1 | 許可読取→実行者停止→停止意図／遮断記録→旧実行者復帰→送出 | B案は許可再利用だけの方式は不合格。最終作用側で旧実行不能を保証する必要 |
| V2 | 遮断記録→許可読取→送出試行 | 読取が最新禁止状態を見て拒否すれば、この単純トレースは合格。V1の解消にはならない |
| V3 | 送出→停止意図→遮断 | 送出済みとして記録し、結果利用拒否へ。未送出だったと記録しない |
| V4 | Bの両Prepare→片側Decision→片側永久喪失 | 残存意図を拒否へ反映できるが、確定段階の曖昧さが残る。許可への推測解決は禁止 |
| V5 | Bの両Decision→受付応答→一地域永久喪失 | 正常手順なら残存Decisionから確定記録を回収可能。ただし旧実行者排除と新規独立保護は別に必要 |
| V6 | HTTP到達→記録前に入口地域喪失→他地域へ再開 | B案は未記録要求の範囲を証明できず、全件回収／安全再開を成立済みにできない |
| V8 | 実行中HTTPがタイムアウト→処理継続→遅延した送信／書込 | タイムアウトだけをフェンスにする方式は不合格 |

V1〜V3は3順序の簡易状態モデルも評価し、V1で遮断後送出が成立する反例1件を確認した。DB・ソケット・IAMの実挙動はモデル化しておらず、この結果を製品試験の代用にしない。PBTへは、保存往復、対象／世代の構造化生成、停止・再開を含む順序列、縮小、seed/pathの再現を引き継ぐ。

## 11. B案の費用と判断

金額・式・未価格部品の正本は[現行費用概算のB案費用](../infrastructure-design/cost-estimate-100-consultations.md#5-b案の費用次回レビュー案)。台帳操作・照合・最終ゲート・networkを積算する。

日本向けSKUと最終ゲートの実構成を確定できていないため、比較は明示した単価・容量仮定の感度で提示する。安価な候補ほど安全要件を満たすとの判断は行わない。旧850 USD・100 USD枠は復活させない。

## 12. 次回レビューでの結論と残課題

B案は従量主体だが障害後の確定・昇格を自作する候補。DB外の最終作用フェンスと記録前受信境界の反例が残り、完成構成の推奨には達していない。

今後は候補Bを対象として、最終作用の保証範囲を定めたゲートと業務書込の原子的境界、入口の記録前区間、地域喪失後の独立保護再構成を設計修正する。成立する構成が得られない場合は、保証する故障範囲または利用停止／受付の条件の変更を具体案として要件レビューへ戻す。今回の方針承認から要件変更を推定しない。
