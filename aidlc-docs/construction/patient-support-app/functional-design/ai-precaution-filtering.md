# AI応答注意事項の条件フィルタリング

## 目的・対象

[注意事項原文](cancer_treatment_precautions_draft.md)の全文を毎回送信せず、固定データと条件判定コードで必要な項目を選び、外部AIの指示領域へ渡す。[AI入力方針](ai-context-policy.md)に追加するU01機能設計である。選別のための追加AI呼出し・ベクトル検索・要約は行わない。注意事項の本文は変更しない。

今回は実装可能なデータ構造・判定コード・受入条件を機能設計に記載する。アプリ用ファイルの生成と外部APIへの接続はコード生成段階で行う。下記TypeScriptは判定仕様を表す記載であり、技術スタックの追加決定ではない。

## 固定データの構成

管理画面や毎回のMarkdown解析は不要。コード生成時に原文を一度分解して固定定数へ転記する。本文の手作業による要約・言い換えはしない。転記処理を使う場合もビルド前の開発用処理とし、本番APIの処理には含めない。

| 種別 | 分割単位 | 選択条件 |
| --- | --- | --- |
| 全員共通 | 「共通事項」の導入文と全箇条書きを1ブロック | すべての対象AI要求で必須 |
| 条件別共通 | 「条件別共通事項」表の1行 | 同じ行の指定軸はAND。同じ軸の列挙値はOR |
| がん種別共通 | 各がん種の共通事項を1ブロック | 確認済みのがん種に一致 |
| 組み合わせ別 | 各「がん種 × 治療時期 × 治療内容」節 | 3軸がすべて一致 |
| 詳細表の前提 | 各副作用表の適用条件、前置き、表外の注意、参考リンク | その表の行を1つ以上選ぶ場合、必ず併送 |
| 詳細表の行 | 副作用表の1行。3列を一体として保持 | 本人確認済みの関連相談と、その行が要求する治療・薬剤群・照射方式／部位等の確認条件を満たす |

原文は14がん種、各16組み合わせ（治療中10種類と治療中以外6時期）の224節を持つ。固定データへの転記時に全節を対応台帳へ登録する。「追加の固有事項なし。該当する共通事項を適用する。」だけの節も台帳には保持し、送信本文からのみ除外する。がん種別共通事項と全員共通事項は残す。

表は見出し・列名も含めて再構成する。「出現時期」だけを切り出したり、前提や否定文を除いたりしない。本文重複の推定削除はせず、同じブロックIDの重複だけを除く。参考資料一覧全体は送らず、選んだ詳細表に付随する参考リンクを保持する。出典リンク先の取得は行わない。

## 入力と条件の確定

C05が本人・SupportSession・ModuleRun・現在の入力版を検証し、当該要求で利用を許可された確認済み属性から条件を作る。ブラウザーが指定したブロックIDや任意の条件は採用しない。別の悩みの属性・古い入力版・AIの推測は使わない。

- がん種は複数選択の集合。アプリの16選択肢のうち、原文に対応する14分類だけを完全一致の固定対応表で引く。不明・回答しない・未登録は「その他」へ変換しない。表記差（例：頭頸部／頭頚部）は承認済み選択肢IDから明示的に対応させる。
- 治療時期は当該悩みの現在有効な1値。時期の「その他」「不明」「回答しない」は各専用値として照合する。未登録・未取得とは区別する。
- 治療内容は治療中の場合の複数選択集合。各選択に一致する共通行・組み合わせ節の和集合を選ぶ。同時実施や、どのがんにどの治療を行っているかは推定しない。
- がん種と治療内容の関連が未取得の場合、選択されたがん種と治療の候補組の注意を併用する。本文を「その治療を受けている事実」へ変換しない。将来、本人確認済みの関連を取得する場合だけ候補を絞る。
- 治療中以外の治療内容は原文の「未取得」を内部照合キーとして使う。残存している以前の治療内容を現在の組み合わせへ適用しない。治療歴がないと判断しない。
- 治療中で内容が未登録の場合、「不明」や「回答しない」を本人に代わって設定しない。全員共通・既知のがん種別共通・成立する時期のみの条件を使う。
- 未知の選択肢ID、不正な形式、不可能な選択集合は検証エラー。正当な未登録は許容する。エラーを全件一致や全文送信へ切り替えない。

「治療中／ホルモン療法／特定がん種列挙」の条件行では、原文の「肺・胃・食道・肝臓・胆のう・胆管・膵臓・血液・骨・軟部組織・脳腫瘍・大腸・その他」を14分類の明示リストへ対応させる。「肝臓・胆のう・胆管」「骨・軟部組織」は各1分類であり、文字の「・」で機械的に分割しない。

## 詳細表の選別

属性別の基本注意は、相談文のキーワードでさらに削らない。相談に関係する内容だけを回答へ反映する指示自体を保持する。詳細な副作用表に限り、確認済みの相談対象と適用条件がそろった行を選ぶ。

細胞障害性抗がん薬、分子標的薬、放射線、ホルモン療法の4表に対して、各行の適用条件を固定のファクトIDで明記する。ファクトは本人確認済み情報をC05が対応付ける。自由文の単純な部分一致やAIの未確認抽出から生成しない。現行画面で確認できない薬剤群等は未取得として扱い、追加の開示を強制しない。

- 化学放射線治療の選択だけで、細胞障害性抗がん薬の使用・外部照射・照射部位を確定しない。組み合わせ節と条件別共通は送るが、各詳細行は必要な確認後に選ぶ。
- 分子標的療法の選択だけでEGFR・VEGF・ADC等の薬剤群を確定しない。原文の「一部の薬剤」の行も、その行の適用が確認できた場合だけ選ぶ。
- 放射線治療は原発がんの部位から照射部位を逆算しない。外部照射の表を小線源・内用療法へ当てはめない。
- ホルモン療法の選択だけで性ホルモン抑制・特定薬剤を確定しない。甲状腺ホルモン補充・TSH抑制へ転用しない。
- 既往治療の確認済み事実が今回の相談に関係する場合、治療後でも詳細行を選べる。日数だけで晩期影響を除外しない。
- 情報不足で詳細行が選べなくても、全員共通の急変時・発熱時の注意は必ず残す。情報確認を連絡・受診より優先させない。

## 条件判定コードの仕様

下記の`catalog`には原文から作る全ブロックを渡す。条件中のキーは画面表示文言ではなく固定ID。`some`は同一軸内のOR、`every`は軸間・必須ファクト間のANDを表す。

```typescript
type Selection = Readonly<{
  cancers: readonly string[];
  phase: string | null;
  treatments: readonly string[];
  facts: readonly string[];
}>;

type Condition = Readonly<{
  cancers?: readonly string[];
  phases?: readonly string[];
  treatments?: readonly string[];
  allFacts?: readonly string[];
}>;

type Block = Readonly<{
  id: string;
  kind: 'global' | 'conditional' | 'cancer' | 'combination'
    | 'detail-context' | 'detail-row';
  order: number;
  text: string;
  when?: Condition;
  requires?: readonly string[];
  noAdditionalText?: boolean;
}>;

function matches(c: Condition, s: Selection): boolean {
  const intersects = (expected: readonly string[] | undefined,
    actual: readonly string[]) => expected === undefined
      || expected.some(value => actual.includes(value));
  return intersects(c.cancers, s.cancers)
    && intersects(c.phases, s.phase === null ? [] : [s.phase])
    && intersects(c.treatments, s.treatments)
    && (c.allFacts ?? []).every(fact => s.facts.includes(fact));
}

function selectPrecautions(
  validated: Selection,
  catalog: readonly Block[],
): readonly Block[] {
  // 実行前に固定データのID一意性・原文対応・条件・依存を検証済み。
  // 入力のID・排他条件・確認元と現在版もC05で検証済み。
  const s: Selection = {
    ...validated,
    treatments: validated.phase === 'during'
      ? validated.treatments : ['not-collected'],
  };
  const byId = new Map(catalog.map(block => [block.id, block]));
  const selected = new Map<string, Block>();
  const add = (block: Block): void => {
    if (block.noAdditionalText || selected.has(block.id)) return;
    selected.set(block.id, block);
    for (const id of block.requires ?? []) {
      const dependency = byId.get(id);
      if (!dependency || dependency.kind !== 'detail-context') {
        throw new Error('PRECAUTION_CATALOG_INVALID');
      }
      add(dependency);
    }
  };
  for (const block of catalog) {
    if (block.kind === 'detail-context') continue;
    if (block.kind === 'global'
      || (block.when !== undefined && matches(block.when, s))) {
      add(block);
    }
  }
  if (![...selected.values()].some(block => block.kind === 'global')) {
    throw new Error('PRECAUTION_GLOBAL_MISSING');
  }
  return [...selected.values()].sort((a, b) =>
    a.order - b.order || (a.id < b.id ? -1 : a.id > b.id ? 1 : 0));
}
```

`when`を省略した非共通ブロックは自動適用しない。条件の空配列も全件一致にならない。がん種別は`cancers`、時期のみの行は`phases`、複合条件行は該当する全軸を指定する。組み合わせ節は必ず3軸を持つ。詳細行には関連相談ファクトと適用確認ファクトをすべて指定し、`requires`で同じ表の前提ブロックを参照する。前提ブロックから他の行を自動選択しない。

原文共通事項は`global`の1件として保持する。データ検証で欠落・空本文・複数登録を拒否する。原文の変更なしではID・本文・条件対応を変更しない。コード内へ本文を直接定数として保持してよく、外部CMSやDBは必要ない。

## 要求への組込みと失敗時

1. C05が最小入力と現在版を確定し、確認済みの条件・相談ファクトを組み立てる。
2. C06の送信前処理で固定カタログを選別し、順序を「全員共通→条件別共通→がん種別共通→組み合わせ別→詳細表（前提を先）」に固定する。選択集合は毎回同じ条件から再現可能とする。
3. 選択した本文をアプリ管理の指示領域に1回だけ組み込む。患者入力は別領域に置き、注意事項や条件の変更命令として実行しない。IDだけを外部AIへ渡して本文を知っている前提にしない。
4. 履歴等と注意事項を合わせた要求全体の入力予算を判定する。超過時は必須注意事項を黙って切らず、送信停止・理由表示・入力保持と既存の短縮／下書き／条件を満たす手入力への導線を使う。全文への切替や追加AI要約は行わない。
5. 要求に`precautionCatalogVersion`・原文SHA-256・選択ID一覧・条件元の入力版／確認済み参照版を対応付ける。患者本文・薬剤名・条件集合を汎用監査ログへ複製しない。選択IDも医療属性を推定できるため、要求管理内の既存の閲覧・保持・削除制御を適用する。
6. 実際に送信したトークン数を既存の要求計測と対応付ける。ローカルな選別・検証失敗は外部APIの送信試行に数えず、送信以降は既存の計数・成否不明・再送規則に従う。

カタログは起動時／ビルド時に検証する。ID重複、条件なし、未対応節、依存欠落・循環、詳細行の前提欠落、共通事項欠落は不正として対象AI送信を止める。入力を保持し、注意事項抜きの送信や全文へのフォールバックはしない。キャッシュを使う場合は共有の固定カタログだけとし、患者ごとの条件・本文を別患者へ再利用しない。

入力の修正後は再選別する。結果適用時も既存の入力版・参照版検証を行い、旧属性で作った遅延結果を適用しない。カタログ更新は新しい版として管理し、旧版要求の再送は元の本文・版に固定する。元版を取得できなければ同じ要求のまま別本文へ差し替えない。

## 受入条件と検証

原文の医学的妥当性の再評価ではなく、転記忠実性・選別・送信境界の検証とする。

| ケース | 期待する選択・挙動 |
| --- | --- |
| 肺・治療中・放射線治療、詳細確認なし | 全員共通、放射線の条件行、肺共通、肺×治療中×放射線。詳細表の照射部位は推定しない |
| 胃と乳房・治療中・手術と免疫療法 | 2がん種の共通と候補4組、該当する条件行を和集合化。同じIDは1回。治療の関連や同時実施は断定しない |
| 治療前・過去の治療内容が残る | 治療前条件と該当がん種×治療前×未取得。治療中の旧選択を除外 |
| がん種不明／回答しない／未登録 | 全員共通と、実際に成立する条件行のみ。「その他」のがん種共通を追加しない |
| 時期不明と時期未登録 | 不明の本人選択には不明条件を適用。未登録では不明を補完しない |
| 化学放射線治療・薬剤／照射方式未確認 | 共通・組み合わせ節のみ。細胞障害性薬剤表や外部照射表を自動展開しない |
| 詳細行の全必須ファクト成立 | 該当行の3列と同じ表の全前提を併送。他の行を混ぜない |
| 詳細行の必須ファクトが1つ欠ける | その行は除外。全員共通の急変注意は維持 |
| 「固有事項なし」の組み合わせ | 固有事項なしの文だけ除外。全員共通・がん種共通を維持 |
| 重複・順序違いのがん種／治療集合 | 選択IDと出力順が同じ。患者入力を変更しない |
| 全14×16の224節と全条件行 | 原文対応台帳に各1件。省略節を含め未対応・重複なし。条件列挙の複合がん分類も確認 |
| カタログ不正・予算超過 | 外部送信0回。入力保持、明示エラー、黙った欠落・全文送信なし |
| 選別後の入力変更・別患者の要求 | 旧結果を拒否。患者間の条件・本文の流用なし |

原文の本文は、改行形式の差を除いて対応元ブロックと照合する。表の分割後もセル全体・前提・否定表現の一致を検証する。費用は全件送信時と選別時の同じ合成要求を比較し、がん種数・治療数・詳細表有無ごとに入力トークン数を測定する。削減率・金額は未測定で保証しない。

## 拡張適合・段階

| 規則 | 評価 |
| --- | --- |
| RESILIENCY-01・02・03 | 適合。C05・C06の既存責務・重要度・可用性／復旧目標・変更管理を維持。固定カタログを版管理 |
| RESILIENCY-10 | 設計上適合。追加外部依存なし。不正・超過時は入力保持して対象送信を止める。既存外部APIのタイムアウト等は後続設計で具体化 |
| RESILIENCY-04〜09・11〜15 | 各N/A。本修正では配備、監視、容量、災害復旧、バックアップ、運用手順・試験を変更しない |
| PBT-02・03・07・08・09 | 各N/A。本段階は設計コードの記載で、アプリコード・テスト基盤は未生成。コード生成時に純粋な選別関数へ必須規則を適用 |
| PBT-01・04・05・06・10 | 助言を反映。順序不変、重複排除、共通事項保持、全条件一致、前提併送、入力不変を性質として後続テストへ引継ぎ |

セキュリティ拡張は状態ファイルで無効につき適用省略。既存の本人・同意・最小送信・版・削除制御は維持する。原文は確認用ドラフトのままであり、本修正は医学的承認・機能設計全体承認・本番利用の有効化を意味しない。
