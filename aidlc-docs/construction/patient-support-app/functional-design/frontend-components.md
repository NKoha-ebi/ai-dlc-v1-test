# U01 フロントエンド機能設計（レビュー案）

デジタル庁デザインシステムを大枠の参照とする既定方針を維持する。本書は画面構成・情報配置・操作・状態の案であり、公式資産の版・ライブラリの採用・全面準拠を決定するものではない。技術選定後に配色・文字サイズ・余白・部品の見た目を実画面で調整する。

質問12追加の遷移・ナビゲーション・入力検証・操作確認・成功・初期／空状態・レスポンシブ・アクセシビリティを以下に統合した。入力長・業務判定は[business-rules.md](business-rules.md)、入出力モデルは[domain-entities.md](domain-entities.md)に従う。

## 画面の階層と配置案

患者側は共通ヘッダー、現在画面の見出し、本文、主操作、戻る／中断を縦に配置。PCでは履歴一覧と詳細の2領域を許容し、スマートフォンでは同じ内容を一覧→詳細で表示する。主操作は各手順で一つを明確にし、省略・戻るを区別する。

管理者Webは共通シェルの中に運営・研究のナビゲーションを役割別に配置する。PCでは左ナビゲーションと本文、狭い画面では展開可能なナビゲーションと1列本文。権限なし項目の非表示とサーバー拒否を併用する。

## フォーム検証・確認操作

患者の自由記述・問い合わせ・返信は空白のみを未入力として扱い、内容を黙って書き換えない。D08の上限はUnicodeのユーザーが見える文字単位で揃える案とし、サーバーとフロントで一致させる。詳細な文字数方式・バイト上限は技術選定で確認する。欄ごとにラベル・必須／任意・エラーを関連付け、送信時はエラー要約と最初の不正欄へ移動する。サーバー検証を必須とし、UI検証だけで受理しない。

- 疾患フォーム：治療中の内容必須、回答拒否と未入力を区別。現在非表示の旧値を無断で確定しない。
- 支援入力：参照元版・本人確認状態を表示。AI案は「未確認」、確認保存後に「内容確認済み」。生成完了だけで保存済みと表示しない。
- 評価：1〜10の整数選択、未回答に0を使わない。再回答は「以前の回答を置換」と表示する。
- 返信：送信前に患者へ公開される本文と対象を確認。下書き保存と返信確定を別の操作にする。
- 公開・停止・権限変更・削除・撤回・退会：対象・変更後の状態・影響を確認する。確認ダイアログの取消はAPIを呼ばない。撤回と削除を同じボタンにしない。
- 記事：タイトル・本文・種別、公開対象版と確認状態を検証。公開中の本文を編集中の下書きで置換しない。

## 共通の表示状態

| 状態 | 表示と許可する操作 |
| --- | --- |
| 初期・未入力 | 目的と最初の操作を説明。入力を要求する理由と任意項目を表示 |
| 空一覧 | 「保存済みの整理はありません」等、空である理由と作成／戻る操作。取得失敗と区別 |
| 読込・処理中 | 操作名と処理中を表示、二重実行を防ぐ。未送信入力を消さない |
| 成功 | 保存済み版・日時または受付結果を表示。削除・撤回の受付と反映／消去完了を別にする |
| 入力不正 | エラー要約・該当欄・修正方法。入力内容を保持 |
| 競合 | 自端末内容とサーバー版の違い、手動解消操作。自動上書きなし |
| 通信断・結果不明 | 「保存できたか確認できません」と表示。同じ要求の結果確認・再接続後再取得 |
| 外部AI・PDF失敗 | 失敗対象と再試行。下書き・確認済み閲覧を維持 |
| 利用停止・権限拒否・同意不足 | 状態と許可された次操作だけ表示。保護対象本文・存在情報を漏らさない |
| 研究無効・集計抑制・0回答 | 条件未承認／提供不可／算出不能を区別。抑制対象の実数を表示しない |
| セッション失効 | 再ログイン後サーバー版を再取得。別人へ端末下書きを表示しない |

保存・成功メッセージは補助技術で通知できる。通知のために画面フォーカスを毎回奪わない。再試行の対象を明示し、別の新規要求を無条件に作らない。

## ナビゲーション・レスポンシブ・アクセシビリティ

P03を患者側の基点とし、現在地・履歴への戻り先を維持する。通常のページ移動で未送信入力がある場合は保存／破棄／移動取消を選べる。これは「戻って前入力を修正する」業務操作とは別で、ブラウザーの戻るだけで生成を呼ばない。復帰時に公開可否・権限・保存版を再取得し、古い画面状態を許可根拠にしない。

スマートフォンは1列、PCは必要に応じ一覧／詳細や左右比較を併用。表は見出しと値の関係を保った一覧・カード表示を用意し、横幅不足で操作が消えない。狭い画面でも編集・確認・エラー・主要操作の順序を維持する。正確な幅・余白・配色は表示レビューで決める。

見出し階層、ラベル、意味のあるリンク、キーボード順序、フォーカスの可視化、モーダル内のフォーカス管理・閉じた後の復帰を設計条件とする。色だけで成功・失敗・選択を伝えない。拡大時の読める配置、エラーの関連付け、読み上げ可能な処理状態を確認する。自動チェックだけで使いやすさやアクセシビリティの達成を宣言しない。

## 画面レビューとPlaywrightの引継ぎ

本段階で画面構成・操作・状態・確認手順をレビューする。視覚モックや実際のブラウザーでの表示確認はまだ実施していない。詳細な配色・文字サイズ・余白・部品選択は技術選定後、コード生成のローカル表示を見ながら確認する。

非機能要件・設計でPlaywright MCPとローカル開発サーバーの接続方法を具体化する。コード生成計画に、合成データで起動→AIの画面操作・スクリーンショット確認→本人レビュー→修正→再確認を入れる。ビルド・統合試験後まで画面確認を延期しない。機能変更は設計を更新し、表示不具合は関連テストとともに修正する。Playwright導入・起動・UI達成検証は現時点未実施。

## Testable Properties

候補選択、表示状態の導出、入力検証、保存状態・期待版の変換は純粋部分の不変条件／往復としてPBT対象。画面の視覚品質・操作性そのものはPBT性質なしとし、実ブラウザーと手動で確認する。特に複数端末の古い版保存、戻る取消でAPIなし、下書き返信の非開示、直接URLの非公開拒否、9／10人と差分抑制、キーボードでの完結、初期・空・成功状態を受入観点に含める。
