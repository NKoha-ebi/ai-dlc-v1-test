# 依存関係・通信・データフロー

矢印は呼出元から依存先。共通行と個別行を合わせて適用し、未記載の横断参照を無条件に許可しない。直接呼出し、サービス経由の論理依存、変更反映を区別する。

| 呼出元（種類） | 依存先 | 関係・境界 |
| --- | --- | --- |
| C01・C02（画面） | C03の登録・ログイン入口 | Context確立前の認証API。入口に必要な公開制御・入力検証を適用 |
| C01・C02（画面） | 役割別業務API → アプリケーションサービス | 認証後の業務経路。公開コンテンツ・問い合わせもサービス経由。画面表示を許可根拠にしない |
| 各サービス（共通） | C03・必要なC04・対象のC12 | 認証・利用状態・役割、必要同意、画面・関連APIの公開制御。必要な判定不能時は充足としない |
| 各サービス（個別） | 対応する業務モジュール | 直接の内部呼出し。個別対応はservices.mdを正本とし、所有元も所有者・業務状態制約を維持 |
| C05（モジュール） | C06 | 内部呼出し。入力版に対応する未確認案を受けC05が管理・保存 |
| C06（モジュール） | 外部AI | アダプターを介した外部I/O。許可タスク・最小入力。認証情報・問い合わせは渡さない |
| PDF取得サービスまたはC07 | C05の確認済み内容参照契約 | 許可されたスナップショット取得。取得主体は未固定。C05の保存領域を直接読まない |
| C07（モジュール） | C15 | PDF成果物を保存する場合だけの保存依存。成果物保存を新たな必須要件にしない |
| 評価サービス | C05、C08 | C05の所有者・完了状態等の参照後、C08で評価制約と最新値置換を維持。C08→C05の直接依存は必須にしない |
| C09（調整モジュール） | 各削除対象の所有モジュール | 要求・対象に対応する削除処理と結果反映。C04・C05・C08・C13等は例示であり全件ではない |
| C04（同意正本）からの変更反映 | サービス・C09・C14・派生データ所有元 | 同意撤回の利用制限を削除と区別して反映。通知・保存方式は未固定 |
| C09からの削除調整 | C07・C14等の保持主体 | 成果物・Projection・キャッシュ等を保持する場合は所有元が処理し結果を返す。非保持時は対象なしを確認。遅延生成・再保存による復活を防止 |
| C10（モジュール） | アカウント情報の所有元の許可契約、C16 | 状態・研究者権限の操作と記録。C03・C10が操作を扱うことだけでは所有元を断定しない |
| C11・C12・C13（モジュール） | C15・C16 | 自身の保存・操作記録。C11は公開状態、C12はページ・API制御、C13は本人・運営権限と返信状態を維持 |
| 研究・提供サービスとC14 | C04、C14の研究条件正本 | 同意・撤回参照と承認済み研究条件参照を分離。研究者権限だけで開放しない |
| C14（モジュール） | C05・C08・他の指標所有元の許可参照 | 管理されたProjectionを含む参照契約。提供時の条件確認・抑制を迂回しない。C13の自動転用なし |
| 信頼されたサービス・モジュール（共通） | C16 | 監査・操作記録と稼働観測を論理分離。本文の無条件複製をしない |
| 各所有モジュール（共通） | C15 | 所有元に限定した保存実装。共有DBでも他所有元の制約を迂回しない |

ブラウザーとAPIはHTTPS、単一バックエンド内は内部契約を前提とする。キュー、通知、同期・非同期、物理DB分割、配備製品は未選定。共通DBと管理されたProjection参照を一律禁止しない。

## 許可3指標の情報源

| 指標 | 論理上の情報源・所有元 | 提供までの経路 |
| --- | --- | --- |
| 利用件数 | 利用の定義に対応する業務記録の所有元。定義と所有元は機能設計で確定。C16観測値を自動的に正本としない | 所有元の許可参照 → 提供サービス・C14の条件確認・抑制 |
| 完了件数 | C05の整理完了状態。集計期間と数え方は機能設計へ | C05の許可参照 → 提供サービス・C14の条件確認・抑制 |
| 整理実感スコア | C08の最新評価と内部集計。対象整理の状態はC05の許可参照で確認 | C08の許可参照（必要なC05状態参照を含む）→ C14の条件確認・抑制 |

利用件数の所有元が確定するまで提供の実装契約は未完成とする。全指標をC05・C08だけが供給すると断定しない。対象人数・期間・同意範囲を整合させ、10人未満と差分推定可能な結果を抑制する。

## データフロー（テキスト）

1. 患者入力 → 必要な共通判定・C05の所有者等の判定 → 入力版保存 → 許可AIタスク → 未確認案 → C05が入力版と対応付けて保存 → 患者本人の内容修正・確認 → 確認済み版保存。受付・生成完了・保存完了を別に扱う。
2. PDF要求 → 必要判定 → C05の公開契約で所有者・確認状態・版対応を満たす内容取得 → C07生成。新たなAI呼出しなし。
3. 通常中断・通信断 → 未送信下書き保持 → 再接続・再認証 → 保存済み版と照合 → 通常再開。端末保存・競合方式は後続決定し、戻る修正と混同しない。
4. 戻る確認 → 取消なら入力・結果を保持し再生成APIを呼ばない。承諾後の入力修正なら関連生成結果を再作成 → 患者本人が再確認 → 対応版を保存。省略する新条件を追加しない。
5. 評価要求 → C05で所有者・完了状態等を確認 → C08が1〜10・最新値置換を適用。平均点×10、0回答は算出不能、未回答・途中離脱は別集計。
6. 本人問い合わせ → 認証・所有者等の判定 → C13保存 → 運営の確認・自由記述下書き → 返信確定 → 本人だけがアプリ内閲覧。下書き非開示。
7. 運営の記事／お知らせ → 権限確認 → 下書き・公開変更 → ページ可否と公開状態を確認した一覧・詳細。非公開時は直接指定でも取得不可。
8. 研究要求 → C03の研究権限・C04の対象同意・C14の承認条件／許可範囲 → 所有元の許可参照 → 識別情報除去・範囲制限済み結果を返す。検索条件・件数・付随情報と個別取得でも制限を維持し別経路で迂回させない。条件未承認なら実データ拒否・合成データで検証。
9. 提供集計 → 許可された情報源から対象期間・人数を整合して取得 → C14の条件確認・10人未満／差分推定抑制 → 許可3指標のみを運営が確認。運営確認・内部集計だけでは提供不可。
10. 削除・退会要求 → サービスが全体調整 → C09が要求と所有元処理を対応付け → 結果・失敗・再試行を追跡 → 全対象確認後に完了。撤回はC04の正本更新から利用制限を別途反映。保持する派生データと遅延AI結果でも削除済みデータを復活させない。
11. 運営メンテナンス切替 → 認証・運営権限 → C12保存・操作記録 → 対象画面・APIへ反映 → 案内。通常停止対象と分離した認証・権限付き解除経路で再公開。

## 障害の波及と未解決事項

認証・保存障害は各業務へ波及する。AI・PDF失敗を下書き保存・保存済み閲覧へ不要に波及させず、PDFを新しいAI生成と結合しない。単一バックエンド停止の全面波及は残り、完全分離は保証しない。判定情報が不明な操作は条件充足としない。判定不能時の応答・再試行・キャッシュ、資源制限、記録障害時の操作別継続条件は非機能設計へ。C12自体の障害から復旧できる運用・インフラ方式は後続で具体化する。

アカウント情報の論理所有主体は既存資料だけでは確定できない。機能設計で正本とC03・C10・C09の参照／更新／削除契約を確定するまで、他モジュールからの直接保存操作を許可しない。利用件数の定義・正本・所有元も未解決として引き継ぐ。研究条件の承認根拠からC14への信頼された反映方式、削除・撤回の通知・保存方式は後続設計で確定する。
## 運営用当月集計の追加差分（US-28）

運営用の参照経路は、C02 O06 → C10入口／運営用集計サービス → C03認可・C12公開可否・各所有元の対象条件 → C05利用／初回完了集計およびC08評価集計 → OperationsAggregateとする。実際の判定順序は機能設計business-logic-model.mdを正本とする。

C05・C08の集計を同じ基準時点・適格条件で対応付ける。Account状態はC03、削除受付・対象範囲はC09等の正本契約で確認し、各所有元の制約を迂回しない。外部提供用C14の研究条件・人数・差分抑制経路とは区別するが、運営用を無条件許可する意味ではない。全患者データの複製・中央集約テーブルは要求しない。
