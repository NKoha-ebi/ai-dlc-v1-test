# ユーザーストーリー作成計画

## 入力と境界

承認済みのrequirements.md、回答ファイル、既存コード分析を入力とする。要件定義書にある機能・非機能要件を拡張せず、利用者の目的と受入条件に変換する。研究条件が承認されるまで実データへの研究アクセスと製薬会社への提供を無効にする要件を維持する。

## 作成方法の提案

利用の流れで章を分け、各章の中では1つの役割の1つの目的ごとにストーリーを分割する。患者の5モジュールを固定順序の必須フローとして扱わない。共通の同意・権限・保存の条件は参照で関連付ける。

| 方法         | 利点                               | 留意点                               |
| ------------ | ---------------------------------- | ------------------------------------ |
| 利用の流れ別 | 中断・再開や前後関係を説明しやすい | 動的フローを一本道にしない           |
| 機能別       | 要件との対応が明確                 | 複数画面をまたぐ目的が分断されやすい |
| 役割別       | 権限の差が明確                     | 共通要件を重複させやすい             |
| 業務領域別   | 患者支援・研究・運営の境界が明確   | 領域をまたぐ同意条件の参照が必要     |
| エピック別   | 大きな目的から詳細を追える         | 大きすぎるストーリーを残さない       |

提案は利用の流れ別を基本とし、患者支援・運営・研究と集計を別章にする。章内は役割と利用目的ごとに分ける。実装の順序・期限・スプリントはこの計画の対象外。

## 表現と粒度

「役割として、目的のために、行動したい」の形式で記述し、識別子、対象ペルソナ、関連要件ID、受入条件を付ける。受入条件は前提・操作・期待結果で表し、正常系に加え拒否・取消・中断・障害時の該当シナリオを含める。1つの利用目的を独立に検証できる粒度にし、依存がある場合は明示する。架空の詳細な人物像や医学的事実を追加しない。
